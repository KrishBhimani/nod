# Remote computers for hosted Sidekick

**Decision update, 2026-09-28:** Continue with Cloudflare Containers for the application and separate owner browser/workspace roles. E2B and other provider changes are deferred; the recommendation below remains historical research, not the current rollout plan. Computer containers start on first use, and the pilot admits eight total provisioned users. Preserve optional adapters and their separate live acceptance gates. See the [current architecture](../architecture.md) and [Cloudflare runbook](../../deployment/cloudflare/README.md).

Research date: 2026-09-26. Repository baseline: `1a471a0f0fa6e986f82a3238a5a83c476d63dc56`.

Status: historical research proposal. The initial snapshot preceded account preparation and implementation. Separate E2B browser/workspace adapters and automated lifecycle fixtures are now implemented; live remote-computer acceptance remains pending. Alternative remote-computer adapters below are still proposals. See the [hosted acceptance record](../testing/results/2026-09-26-cloud-hosting.md) and [account-preparation record](provider-account-setup.md) for current evidence. Vendor documentation establishes available APIs, not that Sidekick works with them.

## Recommendation

Use **E2B as the first provisional managed computer candidate**, with one trusted browser environment and a separate environment for agent shell commands. Compare it with a **full Cloudflare pair: trusted browser plus separate shell** before selecting the production default. Keep the existing local Docker adapters as the default for self-hosted local development. Server startup configuration selects the provider through composition; users never choose it. Add Daytona when its account/network gates are acceptable; treat Browserbase as an optional browser capability.

E2B's documented desktop and pause/resume facilities suggest lower integration risk for preserving Sidekick's trusted browser worker and developer diagnostics. Its [Desktop SDK](https://docs.e2b.dev/use-cases/computer-use) supports a graphical Linux environment and streaming; its [runtime](https://github.com/e2b-dev/runtime) uses Firecracker microVMs. That is an engineering hypothesis, not evidence of better performance, lower total cost, or production readiness. The bounded bake-off must compare complete functionality and measured operating costs.

The decisive architecture choice is **two trust boundaries**, regardless of vendor. A full desktop sandbox that gives the model unrestricted shell access to the same browser profile would weaken Sidekick's existing separation. Cloudflare can host the application while the agent's computers run at another provider.

## What Sidekick needs to preserve

The current [`Computer` and `Workspace` ports](../../src/ports/computer.ts) are already separate. [`composition.ts`](../../src/server/composition.ts) selects the Docker implementations, but also binds a single configured owner. Replacing Docker alone does not create tenant isolation.

| Existing behavior                                                            | Requirement for a remote implementation                                                                                                                                                                                                  |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Computer.act`, observations and screenshots                                 | Retain the existing browser actions and bounded observations; a vendor's pixel-control API is not a drop-in replacement for selector-based actions.                                                                                      |
| Login inspection, exact-origin credential injection, protected-field masking | Run the trusted Sidekick browser worker remotely. Do not expose a generic provider execution handle to the model or client.                                                                                                              |
| Developer control and scoped private input                                   | Require server-authorized developer access for computer control. For any private input, pause the owned task, drain tools, fence its revision and obtain an exclusive lease; resume only after explicit completion and fresh inspection. |
| Native Chromium sign-in without automation/debugging flags                   | Retain control of Chromium's process/profile. An interactive CDP browser alone does not prove parity.                                                                                                                                    |
| Browser profiles, masked screenshots and pending fences                      | Persist privately with an owner and generation; never restore a cached frame as a fresh page or replay credentials after restart.                                                                                                        |
| `Workspace.execute`, files and artifact reads                                | Run untrusted commands away from browser profiles, service credentials, database access and the application filesystem. Preserve process-group cancellation and bounded, symlink-safe artifact copying.                                  |
| Current local task directories and shared tool volume                        | Do not reuse this layout across users. Task folders within a shared shell are not a security boundary.                                                                                                                                   |

The computer remains hidden from ordinary users. Browser frames, desktop viewers and general manual control are developer capabilities, authorized by the server and scoped to owned resources. A normal user can receive a narrowly scoped task credential form when necessary; this does not grant browser access. Provider support for VNC or Live View is an operator/developer capability, not a reason to expose it in the product.

These constraints come from the repository's [provider guide](../../src/providers/AGENTS.md), [replacement guide](../replacing-modules.md), [security model](../security.md), and [production requirements](../production.md). Existing browser namespaces derive from the application data root; they are not authenticated tenant identities. The first cloud version should allocate a browser environment per owned task/profile and a separate shell environment per task. Reusing a shell across one user's tasks can be a later explicit policy; it increases cross-task prompt-injection exposure.

## Provider comparison

### E2B: provisional first candidate

- **Computer and human control:** Linux desktop, screenshots, keyboard/mouse operations and browser-accessible VNC are documented. A custom template can install the current pinned Sidekick Chromium/agent-browser worker. Portability of the existing worker and its native sign-in transition still needs a real test. [Computer use](https://docs.e2b.dev/use-cases/computer-use), [desktop template](https://docs.e2b.dev/template/examples/desktop).
- **Lifecycle:** pause preserves filesystem and memory; paused sandboxes persist until explicitly killed. Auto-pause must be configured because timeout otherwise kills the sandbox. Network clients disconnect on pause and must reconnect. Current documentation also describes a snapshot-backlog fallback to filesystem-only pause, so recovery cannot assume process memory always survives. [Persistence](https://docs.e2b.dev/sandbox/persistence).
- **Network:** outbound internet is on by default. Per-sandbox allow/deny rules are available; domain filtering has protocol/CDN limitations and allow rules take precedence. Test application-level responses, not just whether TCP connected. IPv6 handling remains an acceptance item. [Internet access](https://docs.e2b.dev/network/internet-access).
- **Ingress:** public sandbox URLs are accessible by default. Set `allowPublicTraffic: false`; keep the resulting traffic token in the trusted service. E2B documents an external private/link-local IPv4 deny policy. Sidekick must still authorize each owner, task, frame and input before proxying. [Restricted public access](https://docs.e2b.dev/network/restrict-public-access).
- **Region and capacity:** shared EU access requires Pro or above and support enablement. Hobby allows 20 concurrent sandboxes with one-hour continuous runtime; Pro starts at 100 with 24-hour runtime. This means at most **50 active browser/shell pairs**, before reserving slots for recovery, spare capacity or additional task profiles. It is not a 100-concurrent-user allocation. [EU region](https://docs.e2b.dev/faq/eu-region.md), [billing and limits](https://docs.e2b.dev/billing).
- **Self-hosting:** the Apache-2.0 runtime has a Linux/KVM evaluation package and deployment infrastructure. That package explicitly is not a production deployment pattern. Managed BYOC on AWS/GCP is a separate Enterprise offering; it is not simply local Docker. Retain Sidekick's own Docker path for ordinary laptops. [Runtime source](https://github.com/e2b-dev/runtime), [BYOC](https://docs.e2b.dev/byoc).

Do not copy the public desktop example into a private sign-in flow unchanged: its example VNC process runs without a VNC password. The private ingress gate and Sidekick-owned control proxy must be enforced, and the raw desktop stream must never become the ordinary agent screenshot source. [Desktop template](https://docs.e2b.dev/template/examples/desktop).

### Daytona: full-computer alternative

- **Computer:** documented desktop input, screenshots, accessibility operations and VNC/manual use; custom images require the relevant desktop packages. Sidekick would still bring its trusted worker and native Chromium lifecycle. [Computer Use](https://www.daytona.io/docs/en/computer-use/), [VNC](https://www.daytona.io/docs/en/vnc-access/).
- **Isolation and persistence:** the current default container class has namespace/resource isolation; the VM class has its own kernel. Select and test the VM class when requiring that boundary. Containers preserve files on stop/start and can archive to object storage; memory pause/resume is VM-specific. Do not describe all Daytona classes as equivalent. [Isolation](https://www.daytona.io/docs/en/isolation/), [persistence](https://www.daytona.io/docs/en/persistence/).
- **Network gate:** Tier 1/2 enforce organization restrictions and cannot override firewall policy per sandbox. Tier 3/4 enable arbitrary browsing and configurable allowlists/block-all. The published Tier 3 requirement is a **$500 top-up**, materially different from a small free trial. Establish actual target-site reachability before choosing it for the pilot. [Firewall](https://www.daytona.io/docs/en/network-limits/), [limits](https://www.daytona.io/docs/en/limits/).
- **Region/concurrency:** shared `us` and `eu` regions; concurrent capacity follows allocated CPU/RAM/storage rather than one fixed browser count. Tier 3 publishes a 250-vCPU/500-GiB/2,000-GiB pool. Lower-tier memory values differ between two tables on the limits page, so the console quota is a verification gate. [Regions](https://www.daytona.io/docs/en/regions/), [limits](https://www.daytona.io/docs/en/limits/).
- **Self-hosting:** the documented BYOC architecture puts runners in customer infrastructure while retaining Daytona's control plane. Public SDKs do not establish that the current hosted control plane is independently self-hostable. Confirm current licensing/deployment terms if that becomes a requirement. [BYOC](https://www.daytona.io/docs/en/bring-your-own-compute/), [official repositories](https://github.com/daytona).

Daytona's built-in VNC demonstrates manual control; the reviewed VNC guide does not establish Sidekick-style per-user, revocable viewer credentials. That must be proven through a controlled proxy or an appropriately scoped provider session before private sign-in is enabled.

### Browserbase: optional browser adapter

Browserbase provides CDP-controlled browsers, an interactive Live View and persistent contexts; it is not a full desktop or a replacement for the shell workspace. A context stores cookies and other Chromium profile data and is encrypted at rest. Contexts need strict owner mapping and exclusive use; the docs advise against concurrent sessions using the same context. Native no-debugging Chromium sign-in remains unsupported unless separately demonstrated. [Contexts](https://docs.browserbase.com/platform/browser/core-features/contexts), [Live View](https://docs.browserbase.com/platform/browser/observability/session-live-view).

Session replay and network/CDP logging are enabled by default. The create API exposes `browserSettings.recordSession` and `logSession`; set both false and verify that private input produces no provider recording. The experimental domain allowlist only controls top-level navigation, not subresources, iframes or non-HTTP schemes; it is not a complete egress firewall. [Observability](https://docs.browserbase.com/platform/browser/observability/observability), [session API](https://docs.browserbase.com/reference/api/create-a-session), [allowed domains](https://docs.browserbase.com/platform/browser/security/allowed-domains.md).

The documented maximum session is six hours. Persistent contexts can outlive that session, but an open page's execution state must not be assumed to survive. Regions, availability and exact project settings need confirmation at account setup. Browserbase does not offer ordinary on-prem hosting; open-source Stagehand is a separate component. [Timeout](https://docs.browserbase.com/platform/browser/long-sessions/timeouts), [pricing and hosting FAQ](https://www.browserbase.com/pricing).

Use this option only when the deployment intentionally advertises browser capabilities it can satisfy. Do not make it an automatic fallback halfway through a task: saved credentials, live sessions and approvals belong to the original environment.

### Cloudflare Sandbox/Containers: fewer vendors, more integration work

Cloudflare Sandbox offers Linux command/file/process APIs over Containers, with each sandbox in its own VM. Multiple execution sessions within one sandbox share files, processes and network; they cannot isolate tenants or separate trusted browsing from agent shell. Run separate sandboxes for those roles. The SDK overview has no managed desktop/VNC capability equivalent to the two desktop candidates; installing Chromium/Xvfb and the Sidekick worker is an integration to build and validate. [Sandbox overview](https://developers.cloudflare.com/sandbox/), [security model](https://developers.cloudflare.com/sandbox/concepts/security/).

Container sleep/restart loses local state. Directory backup/restore and mounted object storage address files, not live Chromium memory. Browser profiles require a tested checkpoint protocol with Chromium stopped, encrypted private backups and a restore before use; a bucket mount is not automatically suitable for a live SQLite-backed browser profile. Local backup restore extracts files while production uses an overlay, so local success does not prove identical filesystem behavior. [Lifecycle](https://developers.cloudflare.com/sandbox/concepts/sandboxes/), [backup/restore](https://developers.cloudflare.com/sandbox/guides/backup-restore/).

Outbound policy/interception works in `wrangler dev`, which is valuable for parity. Containers support EU jurisdiction and regional placement constraints. Account resource quotas and supported instance sizes are documented; pilot limits must still be confirmed in Jan's account. [Outbound controls](https://developers.cloudflare.com/sandbox/guides/outbound-traffic/), [placement](https://developers.cloudflare.com/containers/concepts/placement/), [limits](https://developers.cloudflare.com/containers/platform/limits/).

Evaluate Cloudflare's trusted browser and separate shell together in the same bake-off before selecting a production default. Testing its shell alone cannot establish browser handoff, private sign-in, profile recovery, viewer latency or full-pair cost. Compare measured resource use and implementation/operating burden; provider-neutral boundaries permit choosing either result without changing the product UX.

## Provider-neutral design

Retain `Computer` and `Workspace`; introduce the smallest execution lifecycle interface needed above them. Do not replace every provider with a universal VM abstraction. Only composition selects adapters from validated server-startup configuration. The selected provider is installation configuration, never an ordinary user preference. Proposed responsibilities:

| Responsibility              | Contract and state                                                                                                                                                                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owned execution environment | Allocate/locate an environment with server-derived owner, purpose (`browser` or `workspace`), task/profile, region, resource policy and immutable provider/template version. Store opaque provider references in PostgreSQL.                                    |
| Durable ownership lease     | One active holder plus fencing generation. Bind every browser action, screenshot, artifact read, resume and manual input to owner/task/revision/lease. A stale worker cannot reuse a valid provider handle.                                                     |
| Lifecycle                   | Provision, inspect status, suspend, resume, terminate and reconcile unknown outcomes. Record `starting`, `ready`, `paused`, `recovering`, `failed` and `deleted` independently from task status. No replay of an uncertain external action.                     |
| Capabilities                | Advertise tested support for browser observations, masked capture, private manual input, native sign-in, filesystem persistence, memory suspend, egress policy and region. Distinguish configured from verified.                                                |
| Browser operations          | Existing `Computer` behavior through a bounded authenticated transport to the trusted worker. Provider SDKs remain server-side; no arbitrary command endpoint exists for a browser environment.                                                                 |
| Workspace operations        | Existing execution/files interface through a separate sandbox and process supervisor. Preserve cancellation acknowledgement, output limits and regular-file artifact checks.                                                                                    |
| Developer viewer            | Same-origin endpoint or tightly scoped token for one active lease. Require server-authorized developer capability and owner checks before upgrade and throughout its lifetime; revoke on logout, cancellation, lease expiry or release. No permanent share URL. |
| State retention             | Separate private namespaces for workspace checkpoints, browser profiles, artifacts and diagnostic captures. Owner-bound deletion, quotas, retention and audit metadata. Never clone authenticated state into a different owner or a public template.            |

The remote browser adapter should first reuse the trusted browser worker and its fixed operation schema, replacing only the current Docker stdin transport. Reimplementing login/security behavior separately for every provider creates unnecessary divergence. The remote shell can reuse the existing command supervisor's process-group and output guarantees where its runtime permits it. These are proposed implementation strategies requiring compatibility checks.

Task IDs alone are insufficient. Worker jobs must resolve the authenticated owner from durable state and obtain an owner-bound environment lease. Changing operator configuration and restarting the server only changes new allocations; existing sessions keep their recorded provider until explicit migration/retirement. The deployment must retain the adapter needed to drain or retire those sessions safely. Browser profile copying, template upgrades and cookie compatibility need a separate migration path. Exporting ordinary user artifacts is distinct from exporting an authenticated browser profile.

### Idle time, private waits and budgets

Proposed lifecycle policy must distinguish task work from keeping a computer running:

- Suspend an idle shell independently when no command is running. Preserve the acknowledgement rule before suspension; do not terminate a command merely because the chat UI is idle.
- Pause an idle browser only after its operations drain and its state is preserved. A stopped process and a memory-preserving pause have different recovery behavior.
- An active developer manual-control or scoped credential-entry lease keeps the browser available through a bounded expiry. Include that running time in cost estimates. An unused lease expires, clears private viewing/input and leaves the task paused; it must not silently resume the agent.
- Long credential waits can release compute after invalidating the form/control lease and safely checkpointing. Continuing requires an explicit resume and fresh origin/form inspection, with a new request rather than replayed credentials.
- Enforce per-user runtime/concurrency quotas and an installation-wide spending cap, with a small reserve for draining and cleanup. On cap exhaustion, reject new allocations and pause safely at operation boundaries. Reconcile actual resources so failed shutdowns do not remain invisible costs. A provider dashboard alert alone is not a Sidekick budget control.

Exact idle/lease durations and cap amounts remain pilot settings to choose and measure. The bake-off must include active work, idle retention, developer takeover and expired credential waits.

## UX consequences

- Keep the assistant in chat. Ordinary users have no Computer navigation, computer page, provider picker, desktop stream or general manual-control action. The operator's startup configuration defines where execution runs, including local Docker versus a remote provider.
- Keep Profile, Appearance and Preferences in the avatar account dialog. On desktop, preserve vertically centered navigation, hover animation and the collapse/expand icon. On mobile, prioritize chat with a menu for navigation and settings.
- Developer diagnostics may show readiness, leases, recovery, provider metadata and control actions. Production must authorize the developer capability server-side as well as enforce owner checks. A client/query flag can simulate the prototype view but cannot authorize the real routes or expose another user's resources.
- Within that developer surface, distinguish **Paused**, **Reconnecting**, expired leases and stale frames. An unavailable computer produces a concise task retry or failure state in ordinary chat only when the user needs to act.
- A necessary credential or OTP request uses an owned, exact-origin, bounded form. It does not open a general browser surface or expose frames. If a provider/site requires manual interaction that cannot fit this supported flow, fail that operation clearly; do not silently reveal the computer or relax credential protections.
- Keep app login, app consent and remote website sessions separate in the implementation. Provider consent handles permission review; do not add recurring explanations or privacy reassurances to ordinary screens.
- Document provider replacement, capability limits and measurements for operators. Restarting with another provider does not promise that existing browser sign-ins transfer; plan explicit retirement or migration.

## Local development and validation parity

Provide three explicit modes, all exercising the same HTTP features, owner resolution, queues and provider contracts:

| Mode                                                               | Intended proof                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local app + local Docker + disposable PostgreSQL                   | Fast development and deterministic protocol/security fixtures. Existing local networking is not a cloud tenant isolation guarantee.                                                                                                                                 |
| Local app + real remote provider dev project + disposable database | Actual remote lifecycle, worker protocol, developer control, scoped credential forms, file round trip, networking, failures and provider costs without a production deployment. Provider callbacks require only a narrowly authenticated ingress relay when needed. |
| Cloudflare staging/production + same adapters                      | Real ingress, session cookies, proxy/WebSocket behavior, deployment rollback, geographic behavior and deployment-specific resource limits.                                                                                                                          |

Use synthetic fixtures for automated acceptance. Version the browser image/template with the app and pin dependency versions; record them with every live test. Keep provider account limits, private ingress, region and dev key separation identical where practical. A remote provider exercised from localhost still executes remotely and incurs provider usage.

Cloudflare's local outbound interception is documented, but its storage restore path differs from production; test both if selecting it. No provider emulator can prove live account sign-in, latency, isolation of the hosted infrastructure, external service acceptance or the provider invoice. [Outbound development](https://developers.cloudflare.com/sandbox/guides/outbound-traffic/), [backup development](https://developers.cloudflare.com/sandbox/guides/backup-restore/).

## Bounded provider bake-off

After implementation is authorized, compare **E2B and Cloudflare complete browser/shell pairs** against the local Docker baseline before choosing the production default. Add Daytona only when its network tier and spending are authorized. Initial E2B sizing is a hypothesis: 2 vCPU and 4 GiB each for browser and shell; select a supported Cloudflare shape and report its actual allocations, rather than assuming identical instance sizing.

Run at least 30 cold launches and 30 resume cycles per candidate, plus a 60-minute mixed workload at five concurrent synthetic users, two separate environments per active user. Capture p50/p95 cold-ready, resume-ready, action latency, developer frame latency, artifact throughput, failure rate, orphaned resources and metered cost. Measure from the local machine and Cloudflare hosting region. Proposed acceptance targets: 95% ready within 10 seconds cold and 5 seconds resume; developer control input feedback p95 below 500 ms under the target network; at least 99% successful bounded synthetic operations. These are Sidekick targets, not provider guarantees.

| Scenario          | Required evidence                                                                                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Isolation         | Users A and B run simultaneously. Ordinary users cannot access computer views/control even for their own tasks. Authorized developer A still cannot access B's frames/files/status/profile or control B's browser. Neither shell can reach trusted browser control/CDP/profiles or service credentials.            |
| Private sign-in   | Synthetic identifier/password/OTP through scoped forms, then authorized live sign-in where supported. Scan logs, task history, Inspector, artifacts and provider recordings for sentinel secrets. Separately test developer private control; frames disappear on lease release and never enter model observations. |
| Exclusive control | Race agent actions with developer takeover, second tab, logout, role revocation, expiry and disconnect. No agent input while human control is active. Releasing an old lease cannot release a new one.                                                                                                             |
| Cancellation      | Cancel a browser navigation and a shell with surviving descendants; confirm terminal acknowledgement before another operation. A lost acknowledgement fences the environment and cannot produce a duplicate external write.                                                                                        |
| Persistence       | Save a synthetic cookie and task file; pause, resume, restart Sidekick and rebuild its worker. Check profile ownership, explicit recovery, stale frame labeling and no automatic credential replay. Test a filesystem-only restore too.                                                                            |
| Network           | Probe an owned fixture's allowed and denied destinations, private/link-local/metadata routes, redirects, DNS rebinding, IPv6 and cross-sandbox ingress. Validate no provider/admin control endpoint is reachable with useful authority. Do not treat a successful TCP connect as proof of allowed egress.          |
| Files             | Round-trip a PDF/image, verify exact bytes and owner-only download. Reject path traversal, symlinks, device files, oversized/changed files and foreign artifact IDs.                                                                                                                                               |
| Lifecycle/cost    | Exhaust quota, hit timeout, deny billing and kill a worker mid-operation. Queue fairly, show a recoverable product state and reconcile resources after restart. Confirm idle environments stop accruing compute according to the selected policy.                                                                  |
| Replacement       | Run the same synthetic browser/workspace behavior against local Docker and the remote adapter. Restart with another operator-selected provider and start a new task without changing feature code; existing task references remain pinned until explicit retirement.                                               |
| Production proof  | Two authenticated users, including the authorized personal Google test account, ask the assistant to complete browser tasks and create/download artifacts without computer UI. Verify cross-user denial and developer-route protection on the deployed URL.                                                        |

No latency target or test quantity substitutes for the isolation requirements. A single observed cross-user exposure, private credential recording, unbounded viewer URL, or uncertain action replay blocks public signup.
