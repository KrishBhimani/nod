# Hosted integrations, events, and Telegram

Research date: 2026-09-26. This historical proposal inspected public provider documentation and the baseline Sidekick source before hosted implementation or account preparation. The research itself created no credentials, accounts, connections, webhooks, messages or production resources. Current implementation and live-test limits are in the [hosted acceptance record](../testing/results/2026-09-26-cloud-hosting.md); current provider configuration is in [provider account preparation](provider-account-setup.md). Prepared OAuth configurations do not establish completed user consent or event delivery.

## Google sign-in and connected accounts

### Two consent flows

Use a maintained authentication library for an authorization-code flow. Product login requests only `openid`, `email`, and `profile`. Validate signature, issuer, audience, expiry, state, and nonce as applicable to the selected library; issue a secure application session. The durable external identity is Google's `sub` within its issuer, linked to an internal user UUID. Email is display/contact data, not the ownership key. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

Gmail/Calendar connection starts later from an authenticated action. Composio gets the internal immutable UUID as its user ID. Keep explicit connection selection when the user has work and personal accounts. A Google sign-in must not implicitly connect or import Gmail, Calendar, another user's existing grants, or the developer's local Composio accounts.

Composio manages connected-account token refresh; revoked or expired refresh credentials require user reconnection. Its account-expired project event can drive a visible reconnect state. Subscribe only to needed project event types and handle connection lifecycle separately from content trigger events. [Composio authentication](https://docs.composio.dev/docs/authentication).

### Optional onboarding and consent return

Offer all seven supported apps together: Gmail, Google Calendar, Google Drive, Google Docs, Google Sheets, Slack and Notion. Each row shows the account identity and Connect, Connecting, Connected or Reconnect as appropriate. Setup is optional; completing one connection returns to the same screen and leaves the remaining connections available. Provider consent carries the permission review. Keep policy disclosures at the point where they are required and useful; do not repeat login-versus-integration explanations or ownership reassurances across app screens.

A production consent attempt persists the initiating owner/session, app, pending connection, environment, expiry and a server-approved destination such as onboarding or Apps. Use the owned attempt to restore the exact source screen; do not accept an arbitrary return URL from a callback. Resolve success, cancellation, expiry and provider errors into a persisted outcome, re-fetch the owned connection status, and preserve the rest of onboarding. Refreshing the callback or returning in another tab must not duplicate the connection or discard setup progress. A foreign or expired session reauthenticates before seeing the outcome; it cannot adopt the original owner's attempt.

This is a proposed contract. The prototype simulates the consent return locally and does not contact a provider. Live development acceptance must cover all seven apps, return-to-screen behavior, refreshed status, callback reload, cancellation, errors and mismatched identities.

### Managed versus custom OAuth

| Choice                             | Suitable use                                                                                     | Work required                                                                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Composio-managed OAuth             | Controlled rollout where Composio consent branding and shared quotas are acceptable              | Confirm the requested tools fit available scopes; make Composio's role visible before consent; validate real accounts and trigger delivery.                             |
| Custom Sidekick OAuth via Composio | Public product branding, dedicated quota, narrower/different scopes, or faster supported polling | Create environment-specific Google projects/clients and Composio auth configs, configure exact redirects, enable APIs, and complete the applicable Google verification. |

Managed Google polling has a 15-minute minimum. A custom app can use shorter intervals where the trigger supports them; this remains polling. Each custom auth config must be passed in session `authConfigs`; creating it alone changes nothing. [Managed versus custom authentication](https://docs.composio.dev/docs/authentication/custom-app-vs-managed-app).

Use the existing `COMPOSIO_GMAIL_AUTH_CONFIG_ID` and `COMPOSIO_CALENDAR_AUTH_CONFIG_ID` configuration points. Keep other toolkit config IDs operator-controlled. Scope changes affect new authorizations; existing grants need reconnection. Existing connected accounts remain tied to their original auth config when switching OAuth apps, so migration must preserve old configuration until affected users reconnect. [Scope control](https://docs.composio.dev/docs/authentication/controlling-scopes), [OAuth app migration](https://docs.composio.dev/docs/auth-configuration/white-labeling).

### Launch constraints that affect the schedule

- Gmail `gmail.readonly`, `gmail.modify`, `gmail.compose`, and even `gmail.metadata` are restricted scopes; `gmail.send` is sensitive. Reading message bodies cannot be made non-restricted by labeling the assistant read-only. Avoid full `mail.google.com` access unless permanent deletion is an intentional feature. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).
- Calendar has narrower scopes for events, owned events, free/busy, calendar lists, and settings. Choose them from the intended tool allowlist, then test the identity tools and triggers against the same grant; do not default to unrestricted calendar administration. [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth).
- A publicly offered custom OAuth app requesting sensitive/restricted scopes generally requires review. Restricted-data handling on servers brings a security assessment and annual reassessment unless an exception applies. Prepare the public homepage, verified domain, privacy/data-deletion information, support contact, scope justification, and demonstration flow. Do not promise a fixed approval date. [Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
- Development/testing and narrowly defined personal-use exceptions are not public-launch approval. An Internal Google OAuth audience excludes the user's personal Gmail account and arbitrary external invitees. Use External where those users need access. [Sensitive scope verification and exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification).
- External apps in Google's Testing state issue refresh tokens expiring after seven days for scopes beyond basic sign-in. Plan this as a test-environment limitation and exercise reconnect; do not interpret it as a backend reliability bug. [OAuth token expiry](https://developers.google.com/identity/protocols/oauth2).
- Gmail productivity assistance and generative summaries are permitted categories, but Google requires clear in-context disclosure, minimum permissions, controlled data transfer, deletion support, and restrictions on using Workspace data for general model training. The privacy copy must cover the assistant/model processing actually used. Managed OAuth is not a substitute for reviewing Sidekick's own handling obligations. [Workspace data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy).

Composio Cloud retains connected-account tokens even with custom OAuth; Sidekick receives results, not a move of token custody into its database. Its default logs include request/response and trigger payloads; current docs describe retention up to one year. Configure the production project's payload retention deliberately and verify trigger treatment, historical deletion requirements, subprocessors, and model-provider retention. Disabling future payload storage does not delete prior logs. [Token custody](https://docs.composio.dev/docs/security/token-custody), [retention controls](https://docs.composio.dev/docs/security/data-retention).

## Gmail and Calendar events

### Concrete baseline

| Toolkit         | Current Sidekick trigger                            | Current config                                             | Operational coverage                                                                             |
| --------------- | --------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Gmail           | `GMAIL_NEW_GMAIL_MESSAGE`                           | `interval: 15`, `query: in:inbox`, `userId: me`            | New inbox mail is checked periodically. This is not a complete mailbox-change stream.            |
| Google Calendar | `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_SYNC_TRIGGER` | `interval: 15`, `calendarId: primary`, `showDeleted: true` | Changes to the primary calendar are checked periodically; other calendars need explicit support. |

The configs above are verified in current source, not a live provider-schema check. Both toolkits are pinned to `20260915_00`. During implementation, call the trigger-type inspection API for those exact versions and keep sanitized config/payload fixtures. Confirm deletion, recurrence, timezone changes, multiple accounts, initial synchronization, and any backfill behavior through actual test events before promising coverage. Composio documents Gmail/Calendar as polling, with managed-auth latency up to approximately 15 minutes; this is not a delivery SLA. [Trigger model](https://docs.composio.dev/docs/triggers), [trigger configuration](https://docs.composio.dev/docs/setting-up-triggers/creating-triggers).

### Receiver and processing proposal

1. Receive only on the environment's configured HTTPS webhook path. Preserve raw bytes and signature headers through Cloudflare and the application server; cap payload size before parsing.
2. Verify the Composio SDK signature and timestamp. The current protocol uses `webhook-id`, `webhook-timestamp`, and `webhook-signature`; SDK default replay tolerance is five minutes. Keep that tolerance enabled. [Receiving events](https://docs.composio.dev/docs/setting-up-triggers/subscribing-to-events).
3. Resolve an existing subscription from `(environment, provider, subscription ID, connected account ID)`. Its persisted owner is authoritative. Match the signed payload's user, auth config, toolkit, and trigger to that record as additional checks. Never choose the tenant solely from `user_id` in a payload, query string, or model argument.
4. In one database transaction, insert an idempotent receipt and enqueue or mark durable work. Uniqueness includes provider and project/environment; use the stable event/log/provider identity available in the pinned schema. A duplicate yields a successful acknowledgement without scheduling another task.
5. Return promptly after durable acceptance. Database failure returns a retryable error. Never wait for model classification, a remote computer, or the main assistant inside the webhook request.
6. Claim work under a lease carrying owner, connection, and generation. Recheck active account, subscription, ownership, and current preferences before triage and before dispatch. Revocation invalidates queued and in-flight work's authority.
7. Store bounded data only. Separate event receipt, processing state, and user-facing notification outcome; an intentionally suppressed event is successful processing. Apply existing quiet hours/relevance policy and task provenance.
8. Add exponential backoff with jitter, bounded attempts, a dead-letter state, safe operator replay, retention, and metrics for received/duplicate/rejected/queued/oldest-age/failed. Replays preserve the original identity. Retry must not repeat an already approved external action.

These are proposed application requirements. Composio documents at-least-once webhook delivery and stable-ID deduplication. Its public pages inspected here do not establish a contractual retry duration, exact backoff schedule, ordering guarantee, or end-to-end exactly-once delivery. Confirm those operational limits with the provider before assigning a recovery SLA. [Delivery semantics](https://docs.composio.dev/kb/guide/platform-triggers).

The implementation should reconcile desired subscriptions with paginated provider state after startup and periodically. Track connection state, setup failure, last successful reconciliation, last received event, and last processed event independently in backend records and authorized developer diagnostics. An account with no events is not an error. Ordinary app rows remain focused on connection status and actions; do not expose polling cadence, watch setup, receipt timestamps or a verification warning as routine copy. On reconnect, bind the new account/generation and recreate missing watches. On disconnect, revoke local use first, stop watches and delete the remote account with durable cleanup retries, then remove private local data according to policy. Composio exposes list, enable, disable, and delete for trigger instances. [Trigger lifecycle](https://docs.composio.dev/docs/setting-up-triggers/managing-triggers).

### If true Google push becomes a requirement

Keep an event-source adapter boundary, because native push is additional infrastructure and lifecycle work:

- Gmail push uses Google Cloud Pub/Sub and mailbox `watch`; renew at least every seven days, preferably daily. Notifications identify mailbox history, then `history.list` retrieves changes. Notifications can be dropped or delayed, so reconcile periodically; handle stale history via resynchronization. [Native Gmail push](https://developers.google.com/workspace/gmail/api/guides/push).
- Calendar uses expiring watch channels and requires explicit replacement before expiry. Events contain headers rather than changed-event data, so fetch changes separately. Validate channel ID/token/resource ID, tolerate overlap, and reconcile missed notifications. Each calendar's events need a watch; push is not completely reliable. [Native Calendar push](https://developers.google.com/workspace/calendar/api/guides/push).

Do not add native watch-renewal code to the current Composio polling adapter or imply that renewing OAuth tokens renews a native Google watch. Start with the existing Composio model unless measured latency is unacceptable. Time-critical reminders should be scheduled from reconciled calendar data using Sidekick's scheduler.

## Telegram ownership, setup, and delivery

### Proposed first setup flow

1. In the signed-in user's sidebar settings, open **Telegram**. Offer **Connect existing bot** with a direct BotFather creation guide and a masked token field. The token goes only to the trusted server.
2. The server verifies `getMe`, checks the bot ID is not attached to another Sidekick user, and inspects its existing webhook. Show the verified handle. A token is bot control, not identity proof for the intended human.
3. Save encrypted configuration and a stable registration intent before contacting `setWebhook`. Derive an opaque connection-specific webhook URL from the configured server origin, for example `/api/webhooks/telegram/<connection-id>`; the opaque ID selects a record but is not authentication. Generate an independent high-entropy webhook secret for each bot. A hosted user must not enter infrastructure URLs.
4. Show **Link my Telegram account** using a short-lived, one-use opaque `start` parameter. Store only its hash, expected bot, owner, expiry, and setup generation. The parameter can fit within Telegram's 64-character base64url limit. [Telegram deep links](https://core.telegram.org/bots/features#deep-linking).
5. The verified bot webhook accepts the `/start` setup event in a private chat. Record the observed Telegram sender/chat as pending; do not expose any assistant data or execute a task yet. Show the candidate identity in the same authenticated web session and require confirmation, preferably with a challenge displayed in Telegram. This proves control of both sessions and prevents linking by an arbitrary typed numeric ID.
6. Persist the confirmed numeric Telegram user ID and private chat ID. Future inbound messages must match bot, owner, sender, private chat, enabled state, and generation. Reject groups, edits, other senders, unknown bots, and setup-code reuse before task creation.
7. Offer **Send test message** only after pairing. Record request, API acceptance, inbound reply, and result separately; never label API acceptance as proof of recipient delivery. Return a clear success state when a user replies to the test challenge.

Telegram's webhook API uses a secret header, not a body HMAC. Verify it in constant time against the selected bot's saved secret, over HTTPS; parse only after authentication. Deduplicate `(environment, bot ID, update_id)` and preserve normalized message identity. A timestamp is not supplied as an equivalent of Composio's signed replay window, so durable update identity and connection generation are essential. Telegram retains pending updates at most 24 hours; webhook and `getUpdates` modes are mutually exclusive. [Telegram Bot API](https://core.telegram.org/bots/api).

The existing exact-secret reuse and `drop_pending_updates: false` behavior should remain. A lost registration response must not create another secret or silently move a bot. If an existing webhook points elsewhere, show the destination hostname and a separate deliberate move flow. Local testing uses another bot and cannot overwrite the production bot's destination. On removal, disable local use immediately; remove a webhook only after re-reading and matching Sidekick's exact destination/generation, then clear ciphertext after cleanup is durable.

### New token-free option worth a bounded spike

Telegram added managed bots in April 2026. A manager bot with Bot Management Mode can link a user into bot creation and receive a `managed_bot` update; its server can fetch the resulting token. This could support **Create my bot in Telegram** without pasting a token. It introduces a platform manager credential, additional update types, and user/bot ownership and revocation lifecycle. Treat it as an optional follow-up until a separate development manager bot verifies creation, pairing, token replacement, and unlinking. Keep **Connect existing bot** for self-hosters. [Managed bots](https://core.telegram.org/bots/features#managed-bots), [Bot API changelog](https://core.telegram.org/bots/api-changelog).

### Durable send behavior

Keep the existing inbox/task transaction and outbox. Add per-bot/per-chat rate limiting and classify failures: a known rate-limit rejection can be scheduled later; an ambiguous network failure after a send remains uncertain. Honor provider retry timing when available. Never automatically repeat an uncertain message or side effect merely because a worker restarted. Leases need worker identity and expiry so multiple deployed instances do not interfere.

Ordinary bot messaging is free at Telegram's platform layer, within limits. Telegram advises approximately one message per second per chat and approximately 30 per second for ordinary bulk sends; paid broadcast is a separate feature. A personal assistant should batch responses and avoid token-by-token message sends. Hosting, database, model, Composio, and computer execution costs remain separate. [Telegram limits](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## UI states to include in the reviewable prototype

- Google sign-in: initial, redirecting, cancelled, expired session, account restriction, retry.
- First use: one optional screen with Gmail, Google Calendar, Google Drive, Google Docs, Google Sheets, Slack and Notion; chat works without completing every connection.
- Consent return: restore the same onboarding or Apps screen and refresh the owned status after success, cancellation, expiry or error, retaining the other app rows.
- Sidebar account control: Google avatar, name and email, opening Profile, Appearance, Preferences and sign out. Production uses a normalized trusted picture claim and bounded safe loading with initials fallback; the prototype uses local synthetic portraits.
- Desktop sidebar: vertically centered navigation, hover animation and the existing collapse/expand control. Mobile: chat first, with a menu leading to navigation and settings.
- Connected app rows: account identity, Connect, Connecting, Connected, Reconnect and Disconnect. Avoid redundant permission explanations and operational copy.
- Developer diagnostics: separate subscription setup, received-event and processed-event states, without treating an empty account as broken. Require server authorization; a prototype flag only controls a simulation.
- Telegram: verified bot, pairing, waiting for the user's action, expired pairing, confirmed human identity, send test, verified reply, unknown existing webhook, disconnected. Hide infrastructure URLs and numeric-ID entry from ordinary hosted onboarding.
- Approval and reconnect messages: return to the exact owned source screen or task after the secure web flow. Appearance is a per-user preference and not evidence of authorization.
- Computer execution remains behind the assistant. Developers alone can access computer diagnostics/control; ordinary users do not see a provider selector or computer surface. Necessary private credential requests stay scoped to a form.
