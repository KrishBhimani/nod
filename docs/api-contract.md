# Internal API contract

All routes use the same localhost origin and the development account. JSON error responses have `{error: string}`. Browser mutations require same-origin Origin checks. The public URL and non-loopback requests are disabled until real authentication is implemented.

Web routes: `/` chat, `/goals`, `/schedule`, `/vault`, `/apps`, `/channels`, `/vault/:id` secure form (`/credentials/:id` remains an alias). `/browser` shows the shared current browser screen/control view without requiring the inspector flag. `/dev` opens chat with the inspector; `/you` is a compatibility route to chat. Channels has secure setup forms; model provider setup uses server environment configuration. Do not show fixtures as live results.

`GET /api/schedule-runs` and `GET /api/schedules/:id/runs` accept `limit` (1–100, default 20) and an opaque `cursor`, returning `{runs,nextCursor}`. History remains available after a schedule is deleted and returns only owned execution rows.

Vault detail, password, card-number and security-code reads accept a saved entry UUID and an empty JSON object. They resolve the owner on the server, preserve the type-specific authenticated encryption binding, and return fixed errors for missing or unreadable entries. All use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Private Vault lists include full login usernames and masked card metadata; broker login lists and secure account choices retain masked username hints. Login metadata includes optional `identifierLabel`: a normalized observed field label, bounded to 80 characters and retained through staged saving and edits. New manual entries infer Email only for a valid email address, otherwise Username. Legacy private detail/list reads infer that fallback without changing ciphertext. Clients cannot override this metadata. No agent or Inspector tool can call these reads.

Vault updates accept a UUID, a nonempty trimmed name up to 100 characters, a username up to 320 characters and an optional password up to 8192 characters. Unknown fields, including origin and owner overrides, are rejected. An omitted or empty password preserves the latest encrypted password. Updates lock and recheck the owned record after key access, preserve its exact origin and ID, and return only masked metadata with the same no-store/no-referrer headers. Full login usernames may be held in the private Vault page cache; passwords, full card numbers and security codes are excluded. Closing or navigating away fences late edit responses; cancelling an HTTP request does not undo an update already accepted by the server.

Card creates require `kind:"card"`, a name up to 100 characters, cardholder up to 200 characters, card number up to 40 input characters and numeric expiry month/year; optional `securityCode` accepts three or four digits. Numbers normalize spaces/hyphens to 12–19 digits, reject repeated digits and require Luhn. Expiry ranges from the current month through 30 years ahead. Card updates use `VaultCardUpdate`; blank or omitted `cardNumber` preserves the latest locked value. Unknown fields, including owner and origin, are rejected. An omitted or blank `securityCode` preserves the latest locked value; `null` explicitly removes it. Details return only `hasSecurityCode`; neither lists nor create/update replies contain code presence or value. Cardholder, number and security code are encrypted together. Create/update replies never include the cardholder or full number. Cards live separately from website logins and cannot be used by secure login selection or automatic fill.

See `src/shared/contracts.ts` for response types. Attachment-only messages are accepted; empty messages without attachments are rejected. `Message.streamId` associates a persisted reply with its transient stream. Action confirmations are ordinary `/api/messages` yes/no submissions. They bind to the latest owned pending confirmation in that channel, or its explicit reply target. The saved action, account and arguments execute once in a durable worker segment; there is no approval HTTP endpoint or separate approval page. Paused schedule records remain editable; DELETE removes the schedule but retains its run snapshots. `Schedule` includes `kind`, nullable `cron`/`runAt`, `revision`, exact `nextRun` and `lastRun`. One-off `runAt` must include a UTC offset and be in the future when created or resumed; the saved timezone remains available for display. `ScheduleRun` includes title, schedule ID, execution task ID, due time, timezone, creation time, status and fixed task error. Status describes execution, not inferred user success. Revision checks reject stale jobs after edits, pauses or deletion. Already dispatched executions continue independently.

Messages belong to one visible conversation per channel. A short answer follows the latest visible assistant question. An explicit `replyToMessageId` must reference an owned message in the same channel; it resumes idle work, queues a related input behind active work, or starts new work for a cancelled session. When configured, bounded semantic routing can associate other follow-ups with a new or existing owned outcome. Related inputs can wait behind credential/approval/manual steps without resuming those steps; secure waits retain their explicit credential-form requirement. The response includes the internal task ID, but there is no task picker or ambiguous-task response. Credential and manual-control waits require their dedicated path. Confirmation replies use the same message route with owner, channel, generation and revision checks. `Message.replyTo` includes a bounded quoted preview; `Message.reactions` contains user and assistant reactions. A changed user reaction can wake one quiet event task; repeating or removing it does not. Assistant reactions target only visible owned user messages in an active direct-user web segment and never wake another task. Each message permits one reaction, with a durable five-minute cooldown between new reactions; unsupported channels skip the operation. Message history uses the oldest message's timestamp and ID together to avoid duplicate or omitted rows at timestamp ties.

Implementation ownership and change guidance live in the area's `AGENTS.md`, linked from the root guide.

`clientMessageId` becomes the persisted user message ID and lets the client reconcile an optimistic bubble with HTTP or SSE updates. Omit it to receive a generated ID. An identical retry returns the original accepted message and execution without enqueuing work again. Changed text, ordered attachments, reply target, owner, channel or conversation generation return 409; reset never permits replaying an archived message ID into the new conversation. Accepted user execution failures publish one concise, fixed assistant reply through the normal channel path. Stale, cancelled and background executions do not publish that failure reply.

Inspector response types live in `src/shared/inspector.ts`. Observation cursors require both timestamp and ID. Each unfiltered page contains at most 100 combined tool and model records, newest first, with a cursor for earlier records. `tool` selects that registered name's tool-call pages. Summary totals and `toolUsage` counts cover all retained records for the owner or optional owned task, independent of the current page/filter. The UI has Screen, Activity, Tools, Costs and Prompts tabs. `costUsd: null` means unavailable, not free. Selected-task assistant response costs are SDK estimates, not invoices or per-tool charges. The catalog is available before the first task and does not execute tools. All inspector endpoints return 404 when disabled and use the same local access checks as other API routes.

`GET /api/inspector/work` takes no scope/query arguments and returns `InspectorWorkResponse` from `src/shared/inspector-work.ts`. It contains up to 12 current owned active outcomes/requests with pending input counts, eight enabled schedules with persisted next times and queued state, actual review registration and the latest eight decisions from the last 24 hours. Each list includes its full total. Active executions are grouped by owned outcome and filtered to the current conversation generation. Labels/reasons are redacted and bounded; raw task prompts/event summaries are excluded. Review status is null when unavailable and never invents a next occurrence. It is read-only and no-store.

`src/shared/provider-usage.ts` defines provider summaries and coverage rows. The wire field `requests` counts adapter operations, not billable network requests; internal SDK calls can differ. Rows include failure/cancellation counts, duration, nullable metrics, `costUsd`, `pricedRequests` and `pricing` (`reported`, `sdk_estimate`, `mixed` or `unavailable`). Pi-reported compaction/cache-warming usage appears here separately from assistant-response totals. Speech seconds/prices, SDK-internal requests, hosting and invoice data remain incomplete or unavailable, as coverage rows state. Recording is private, enabled-only, numeric/bounded metadata retained for seven days; provider arguments and manual input text are excluded. `droppedEvents` signals incomplete capture and old activity is not backfilled.

`src/shared/link-preview.ts` defines `{url,title,description?,siteName?,imageUrl?}`. Image URLs are only `/api/link-preview/image/<UUID>`, never a caller-supplied proxy URL or remote source. Metadata and images use public-address validation, pinned DNS resolution, bounded redirects/size/time and no browser cookies or page JavaScript. Known local, sign-in, consent, Vault, approval and token-bearing URLs are excluded; arbitrary public URLs can still contain private text unknown to these heuristics. The client requests at most two previews per persisted message near the viewport and keeps original links when metadata is unavailable.

Connections return one row per saved account, plus a disconnected service row when no account is saved. `connectionId` is the local account selector; `accountName` and `accountEmail` come from the provider. Google tool arguments may include `connectionId`; multiple accounts require a selection, and write approvals retain it. The server removes this selector before calling the provider. Watches are always requested for supported services. `triggersActive` and `triggerStatus` distinguish actual subscriptions from pending or unavailable delivery configuration. Legacy service-only disconnect and trigger endpoints reject ambiguous accounts. Onboarding offers connection links in chat and can read connected data, but cannot create a connected-data write approval or execute a write.

Manual browser control uses a 30-minute lease and exact task revisions. Ownership and the paused state are rechecked on every input and resume. Start waits up to ten seconds for runtime actions to drain; failure leaves the task paused. Restarted or expired leases require reacquisition, while explicit resume remains possible. Manual inputs are not stored in messages, events or observations.

`POST /api/credential-requests/:id/refresh` re-inspects the current login page without entering credentials. It locks the owned task and pending request, checks its revision, status, expiry and exact origin, and returns updated field and method metadata. Stale requests cannot refresh.

Pending non-OTP `CredentialRequest` responses can include `savedEntries` metadata and a `selectedEntryId`. Entries must match the owner, exact origin and any staged identifier. They contain names and masked username hints, never passwords or full usernames. Saved selection uses the same one-use token, revision lock, fresh page inspection and continuation path as direct entry. A new login does not overwrite another entry on the same website.

Identifier-step submissions accept `{label,username,password}` so one secure form can cover a staged login. Only the identifier enters the first observed page; an encrypted, expiring server-side selection supplies the later password step once after fresh inspection. It survives broker restart and is cleared before password injection. OTP input is separate and never persisted. Sign-in and verification methods are chosen in chat before requesting Vault.

Credential submission normally returns `{ok:true}`. A recognized fresh website rejection returns HTTP 200 with `{ok:false,retryUrl,error}`. The old token is consumed, the replacement `/vault/<token>` keeps the same owner, task revision and original expiry, and the task stays waiting without a model resume. Rejected passwords are not saved. The client clears entered values and loads the replacement form. Submission is not proof of successful authentication; delayed or unrecognized results still require browser inspection.

`POST /api/conversation/reset` with `{}` returns `{ok:true,conversationRevision}`. It archives the current web chat, cancels its active work and invalidates old waiting continuations. It preserves messages in storage, saved accounts, Vault entries, profile/memory, goals, schedules and other channel conversations. No restore button or permanent deletion is implemented. `AppState.conversationRevision` and SSE delta `conversationRevision` let clients reject old state and stream callbacks. Message submissions, history requests and onboarding accept an optional `conversationRevision`; a stale value returns 409. Reply targets and reactions cannot address archived messages.

Reaction values must be one Unicode emoji grapheme, including supported joined sequences, modifiers and flags. Legacy like/dislike/heart values map to their existing emoji and deduplicate against the equivalent emoji. Vault invitations name the broker-observed site and step; sign-in method choices stay in chat before an invitation. Arbitrary page labels and secret values are excluded.

`GET /api/inspector/prompts?taskId=&before=&beforeId=` returns bounded private prompt snapshots for the owner, optionally scoped to one owned execution, with combined timestamp/ID paging. Capture and access require the developer inspector. Responses are no-store; system/instruction text and titles are redacted. Images and saved provider transcripts are omitted. `GET /api/inspector` also exposes owned `currentBrowser` metadata from actual browser activity independently of a diagnostic task filter. Tool observations accept no taskId for an owner-wide view and return direct provider-operation counts and cost per tool/call; overall cost comes only from `/api/inspector/providers`.

Native sign-in uses the same revision-bound takeover lease. Input requests in `sign_in` mode go only to the private container desktop adapter. Its dedicated frame route rechecks ownership, revision and expiry after capture and never retains pixels. Ordinary screen capture returns 423 while native sign-in is pending, including after a restart. Expiry, cancellation and reset close the owned window without restoring automation. Explicit continuation waits for its process to exit and preserves the pause on failure. Core browser routes are available without `DEV_INSPECTOR`; Inspector-prefixed control aliases and diagnostic routes remain flag-gated.
