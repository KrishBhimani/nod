# Sidekick system guide

Updated **2026-09-25**. This is the living product and technical reference for the current repository. Update it when behavior, dependencies, boundaries, or validation changes. [Verification](verification.md) records test evidence; configuration alone is not proof that a provider works.

Sidekick is a local, single-owner assistant. One chat holds messages, replies, attachments, and reactions. Internal tasks supply durable execution, independent browser sessions, workspaces, action confirmations, and continuation. Pi runs the model/tool loop; trusted server services control credentials, connected accounts, storage, and background work. The web app binds to loopback and has no public app authentication.

Pending and sent images, audio, video and PDFs share one keyboard-accessible viewer. Galleries have bounded tiles; at most four are shown with an overflow count for larger sets. Sidekick's viewer shows only a counter and controls, without visible filename or size metadata. Arrow keys change the attachment without moving focus; Tab still reaches controls, and Escape closes and restores focus. Audio/video use native controls. PDFs load PDF.js only when opened, using a bundled local worker and a bounded canvas page with Previous/Next controls. Page controls do not change the selected attachment. Failed PDFs offer retry and download; closing or changing attachments cancels rendering and destroys the document worker. Document scripts and XFA are not enabled, no remote worker or assets are configured, and artifact CSP stays unchanged. Unsupported types remain download tiles. Previews accept supported MIME types and owned artifact URLs, or composer-created local blob URLs before upload; arbitrary remote URLs and active HTML are not embedded. [Attachment viewer](../src/web/components/attachment-images.tsx).

Goals, Schedule and Vault share the same empty-state baseline at desktop and phone widths. Goals and Schedule use one tab geometry; Vault reserves the same controls space without adding a tab. Page headers have no manual refresh button. Apps, Goals and Schedule retain cached data and update silently through the existing refresh stream and window focus. Channels rechecks on mount, focus and accepted setup changes.

Message Markdown and supported HTML are sanitized. Remote Markdown images are not fetched automatically. File uploads are limited to five per chat submission and 15 MB each. The composer keeps newly entered text if sending an earlier draft fails. [Chat code](../src/web/pages/chat.tsx), [composer](../src/web/components/composer.tsx), [message rendering](../src/web/components/message.tsx).

Reactions start with six common emoji and a More button beside the message. More loads the searchable category, flag and skin-tone picker without a modal backdrop. Selecting the same emoji removes it. Outside click and Escape dismiss it, with focus returned after selection or keyboard dismissal. Public link cards load near the viewport, at most two per persisted message, using escaped metadata and opaque local image-proxy URLs. Known secure, approval, login and private destinations are excluded; unavailable previews retain ordinary links. Secure credential invitations show the destination and Vault link without a website preview card. URL screening cannot recognize every private value in a public URL.

The sidebar owns navigation and Inspector access; there is no duplicated app header. Outside editable fields, Cmd on Mac or Ctrl elsewhere plus J opens Chat, G Goals, S Schedule, E Apps and D Channels. Vault, sidebar collapse and Inspector use their buttons without app shortcuts. Holding the modifier for 650 ms reveals letter hints, outside the icons when collapsed. Ordinary shortcut taps do not reveal them, and editing suppresses navigation shortcuts and hints. Links expose labels, current-page state and available keyboard shortcuts; arrow keys, Home and End move navigation focus. Larger navigation icons include PlugZap for Apps, while pink marks selected navigation. Primary actions are pink in light mode and lavender in dark mode. Icons tilt and grow on hover, with a smaller press state. Only the graphic moves; the navigation target and pointer stay stable. Reduced-motion preferences disable these transforms. [Shortcut mapping](../src/web/lib/navigation.ts).

At widths of 640 px or less, navigation becomes an icons-only bottom bar with six page links and More. More contains Inspector when enabled and Get started. Accessible labels remain; desktop branding, collapse controls and shortcut hints are hidden. The bar accounts for device safe areas. [Sidebar](../src/web/components/sidebar.tsx).

Every **Get started** entry uses the same reset-then-onboarding flow. Reset archives the current web generation, cancels pending work and invalidates old continuations, then setup starts with the returned revision. Accounts, Vault, preferences, profile/memory, goals, schedules and other channels remain intact. Messages remain stored for a future restore path; no restore UI or permanent deletion exists. State, history, drafts/submissions and streams are fenced by `conversationRevision`. This flow was checked with synthetic fixtures; no live owner reset was performed.

Manual browser takeover pauses the task, bumps its revision, drains active tools, and acquires an owner-bound 30-minute control lease. Click, type, key and scroll inputs are serialized; release and explicit resume return control to the agent, which must inspect first. Status checks release stale leases after cancellation, reset or changed ownership/revisions; serialized cleanup cannot release a newer acquisition. Current fixtures cover the container transport, private desktop lifecycle and control boundaries. Earlier real-browser runs used synthetic forms and their listed source versions; they do not prove the new container path or real website authentication. Older verification entries for a formatting preview, date picker, or task picker also describe a previous UI; those controls have been removed.

## How one chat becomes durable work

1. The server accepts an owned message, attachments, and optional `replyToMessageId`. It validates the reply target and derives task routing; the UI does not expose those internal task choices.
2. A PostgreSQL transaction persists dispatch state and a pg-boss job. Four workers can run independent tasks. Each task has a revision, a private transcript reference, and a workspace/browser identity.
3. The runtime supplies bounded context and explicit tools to Pi. Provider keys are injected into trusted adapters, not model prompts. Tool calls route through capability interfaces and server policy.
4. Typing and deltas show live work. The agent can send a concrete progress update when useful; elapsed time never inserts a generic promise. Background work stays silent unless it has a useful result or needs an answer. Text deltas use a distinct stream ID per model message. Persisted messages reconcile those IDs so a late refresh cannot erase another message's stream.
5. An ordinary question, secure credential step, or action approval pauses execution. The appropriate server path records the answer/outcome and schedules continuation. Task revisions reject stale jobs and forms.
6. Cancellation stops further accepted work. Already accepted external actions can finish. Recovery treats interrupted external outcomes as uncertain instead of silently replaying them.

Explicit replies carry a bounded quote in the message DTO, including when the original is outside loaded history. A same-channel reply resumes its target task when that task is waiting for an ordinary answer, succeeded, or failed. Running, queued, or cancelled targets create a new internal task while retaining the quote. Credential and manual-control waits use their dedicated secure paths. Action confirmations use yes/no replies in the same chat, bound to the exact pending action. An implicit short answer follows only the latest visible assistant question in that channel; other messages start internal work without showing a task picker.

User reactions accept one Unicode emoji on assistant messages, including joined sequences, flags and skin tones; legacy `like`, `dislike` and `heart` values still render and deduplicate. The agent can occasionally react to a visible owned user message in web chat. The server permits one reaction per message and at most one new reaction per five minutes, with owner, channel, generation and active-segment checks. Removing a reaction does not reset those limits. Telegram, WhatsApp and background runs skip this tool until provider reaction support exists. A changed, non-null user reaction can start one quiet event task when the main model is configured; repeating or removing it does not. Agent reactions do not wake another task. Reactions are feedback, never action authorization. [Task routing](../src/server/tasks.ts), [runtime](../src/runtime/index.ts), [wire contract](api-contract.md).

The runtime limits a segment to 60 tool calls, 60 model turns, and approximately 12 minutes. Shell commands have a maximum 120-second timeout. These are execution bounds, not response-time promises. The current catalog and schemas come from [runtime/tools.ts](../src/runtime/tools.ts); the inspector reads that same catalog.

Resumed sessions reload current instructions and bounded recent conversation context. Recent text from the same owner's other verified channels is available as data, excluding archived web generations, action-target IDs and provider sender/account identifiers. This does not grant cross-channel continuation or write authority. Tested requests for login details are redirected to inspected Vault entry, with sentence-buffered output checks. This is a bounded language safeguard, not a universal prompt-injection or secret-disclosure filter.

| Browser                                                                                                                                                                                    | Linux workspace                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Task-specific Chromium profiles inside `sidekick-browser`, controlled through the trusted `agent-browser` adapter and fixed Docker-exec RPC.                                               | An unprivileged Node user in the shared `sidekick-workspace` container.                                                                                            |
| DOM/text snapshots and masked screenshots; fixed open, snapshot, click, fill, and scroll actions.                                                                                          | Node, Python, pipx, git, curl, ffmpeg and package installation through npm/pipx.                                                                                   |

The browser has a separate process, mount and network namespace from the untrusted workspace. Its private `browser-data` volume and Unix control socket are not shared with that shell, and no browser port is published. The host bridge sends only validated operations over stdin and waits for cancellation to drain remotely. An uncertain transport failure stops further requests until restart. This is not native control of the user's Mac; the only desktop view is the restricted browser sign-in session. Workspace tasks share one container/user and installed tools, so directory naming is not hostile-task or tenant isolation. Network access can transmit accessible data and reach other services on the Compose bridge, including PostgreSQL. PostgreSQL requires a generated password held in private server configuration; the browser and shell receive no database credentials. This uses database authentication rather than network isolation. Browser credential masking covers tested DOM cases, not every hostile page/canvas behavior. [Security](security.md), [workspace adapter](../src/providers/docker/index.ts), [container bridge](../src/providers/container-browser/index.ts).

Ordinary automation uses headed Chromium on a private authenticated Xvfb display for each task in the Linux container. Browser closure also releases its display; failed closure keeps the display for a cleanup retry. This remains automated CDP access. Native sign-in closes that browser and display, then uses the same executable and profile on a separate private display without debugging or automation flags; continuation creates a fresh automated display. The container drops capabilities, prevents privilege escalation and limits resources; Chromium's internal sandbox is disabled, so the container is its operating-system boundary. Provider keys and the Vault master key remain in trusted host services. Existing host browser profiles are not migrated. Earlier headed-Mac website checks are historical evidence and do not establish current container acceptance.

**Take control** opens the current profile in the private workspace browser desktop. It is available even when a screenshot is unavailable or no browser task exists. Active work pauses and drains before control starts; use **Resume agent** to return control. Finished work keeps the same page and profile, and **Done** restores ordinary masked viewing without restarting the task. With no current browser, control opens an owner-bound blank workspace session; **Done** closes that session without creating a task. The private input controls remain disabled until a fresh frame is available.

The core `/browser` page is available without Inspector. It uses container Chromium, keeps private control frames out of model screenshots and artifacts, and restores the task browser only after a normal browser quit completes. A quit timeout keeps work paused. Native frames clear when the app loses focus or the selected session changes. New browser launches are capped at four tracked live sessions per Computer; capacity closes an idle unheld session or rejects the launch when all sessions are protected. Profiles and masked last-known images remain, but a later task may need to reopen its page. The restoration preference survives idle cleanup and service restart; in-memory page state is not guaranteed. Recognized browser-security rejections stop repeated Vault requests and explain Take control. Connected Apps remain the preferred route for supported Google API work; they do not sign in to unrelated websites. [Verification](verification.md) tracks container evidence; synthetic passwords and fake 2FA do not establish live provider acceptance.

## Vault and action confirmations

Website passwords use AES-256-GCM with a random 96-bit nonce and authenticated owner/origin/record binding. The master key lives in macOS Keychain, or an explicitly supplied 32-byte base64 `SIDEKICK_VAULT_KEY`; it is not stored with database ciphertext. Channel settings use the same key source with a distinct owner/channel binding.

Vault is the default path for supported website sign-in. Before the agent suggests manual browser sign-in, the runtime requires a fresh trusted login inspection. Reachable login fields produce a secure link in chat. Navigation or inspection failures request bounded recovery and cannot be presented as a confirmed browser-security rejection.

Each saved login has a user-defined name and an exact website origin. The manual form accepts a domain such as `example.com` and stores `https://example.com`; subdomains, schemes and ports remain separate. Multiple named logins can share an origin. Secure forms show the fixed destination and collect an item name, identifier and password together, including when the website initially shows only its identifier field. If several saved accounts match, the owner chooses one in Vault. The broker keeps the selected account through staged sign-in; OTP entry never saves a login.

The private Vault list shows full login usernames and exact websites. Add item offers Login and Payment card. Rows open directly as editable forms, with Save changes shown only after an edit. There is no row-level delete action, and deletion requires a separate confirmation inside the modal. Passwords, card numbers and optional security codes remain hidden until Show or Copy; separate owner-bound requests return each secret. Copying while hidden does not reveal it. Closing or leaving the view clears secret state and rejects late responses. Passwords, full card numbers, security codes and code-presence flags never enter the page cache, chat, agent tools or Inspector. The system clipboard is used only for an explicit copy action.

The form edits Item name and login or card fields while keeping a login's website fixed. Where available, the saved website label identifies the login field; otherwise it says Username. Saved secrets start masked. Change opens a required empty replacement field; Cancel change restores the unchanged state without retrieving the secret. Card security codes also support Add and Remove, with removal applied only on Save changes. Cancel changes restores saved nonsecret values and clears replacements. The trusted server locks and rechecks the owned record, retains its encryption binding and returns masked metadata only. The list updates after an accepted save; replacement input is cleared on submission and when the window is hidden. These edit boundaries have focused UI and disposable-database coverage; real website acceptance of changed credentials is a separate check.

The [Vault acceptance report](testing/results/2026-09-25-vault-accounts.md) records public X login-page access, the real app's Vault invitation, and synthetic password/OTP completion with named account selection. Its source snapshot passed 505 local tests. This does not establish real X account authentication or bookmark access.

The later [Goals, Schedule and sign-in report](testing/results/2026-09-25-goals-schedules-auth.md) repeats password and fake-2FA rejection/retry, browser continuation and screenshot delivery. It also records the Goals create/update/pause/resume/complete UI, one-off and recurring execution, history, keyboard access, narrow layouts and connection recovery. That source snapshot passed 534 tests; real provider authentication remains unverified.

Secure forms use a random token whose hash is stored, expire after ten minutes, and bind to the task revision. The broker observes identifier, password, and OTP stages and rechecks the current origin/fields before entry. OTPs are not saved. Observed method choices stay in chat and can start a website OAuth or verification flow; that does not prove login or establish a Composio connection. For staged login, the broker holds the supplied password encrypted under the same owner, origin, revision and original expiry, then consumes it before filling the freshly observed password field. Broker restart does not require another password form. Rejected or uncertain attempts require fresh input, and OTP remains separate. Secure injection locks observations, and the model receives no plaintext credential result.

A fresh visible rejection detected within two seconds consumes the old form and returns a new Vault URL with the original expiry and revision. The UI clears rejected values and shows the retry form; the task stays waiting and no rejected password is saved. Unknown or later website responses remain submitted, not authenticated, and require the agent to inspect the current page.

The trusted server and destination website necessarily handle plaintext. Encryption does not hide it from a compromised host or a cloud operator controlling the authorized decrypting service. Cloud KMS alone does not change that limitation. Key rotation, cloud envelope encryption and operator-resistant execution are not implemented. Payment cards use a separate AES-GCM table with an owner/record/type binding. Card lists show name, brand, last four digits and expiry; explicit details add the cardholder and a security-code presence flag. Separate no-store reads reveal the number or optional three/four-digit CVC/CVV. Card creation and edits validate bounded fields, normalized numbers, Luhn, expiry and security-code format; omitted or blank replacements retain the latest stored value, while an explicit null removes the code. Cards cannot match website-login queries. Card autofill, TOTP seeds, iframe/split-code login, passkeys and hardware-key flows are not supported. [Vault details](vault.md).

Known ordinary app and personal actions can execute directly when the current owned user instruction requests that operation and scope. Draft requests do not authorize sending. Unknown, destructive or unmatched actions ask one specific question in the same chat, showing the saved action details and account. A yes or no binds to that owned confirmation and execution revision. The worker executes the saved snapshot once, outside the message transaction. Credential and manual-control resumes can retain a known ordinary app request only through a server-marked exact revision and its original owned source message. Personal facts and generic resumes do not inherit this authority. Completed action snapshots are not executed again after a resume. Uncertain outcomes are not retried automatically. External content, onboarding, generic background events and reactions cannot authorize writes. A scheduled run can execute a known ordinary app action only when its immutable saved user instruction and operational prompt both authorize it; draft/no-send and cross-app mismatches remain blocked. Source-checked personal self-statements retain their existing quiet-save path.

Goal create/update and schedule create/update/cancel are validated reversible local actions. They run within the exact owned current user segment without a natural-language phrase gate or an extra confirmation. The model is instructed to use reads for review-only requests, respect no-change and draft-only requests, and ask when the intended change is unclear. These instructions are not a semantic or prompt-injection guarantee. External app writes retain the conservative operation, scope and catalog checks. Goal and schedule rows also offer Delete with one local confirmation; deleting a schedule cancels future jobs and retains execution history.

## Apps and event delivery

Composio holds and refreshes app authorization. Sidekick stores provider-tagged account/session references and supports Gmail, Calendar, Drive, Sheets, Docs, Slack and Notion, including several accounts per service. Consent scopes and provider availability still constrain each action.

The agent first uses `SEARCH_TOOLS` for current schemas. A fixed read allowlist executes directly. Known ordinary writes use the direct-user action policy; other actions use chat confirmation bound to the exact local account ID. Switching providers requires account migration/reconnection; an adapter replacement cannot transfer OAuth tokens or reuse another provider's IDs.

`manage_apps` lists actual connected accounts and starts a chosen service's hosted consent link. Onboarding reads a bounded amount of relevant connected app data to propose useful work. Its server context rejects connected writes before an approval can be created. The onboarding endpoint supersedes prior onboarding tasks; the user-facing Get started flow first archives and cancels the previous web generation.

Gmail, Calendar, Slack direct-message and Notion page-content watches are requested by default where supported. Active delivery also needs a signed webhook configured for `/api/webhooks/composio`, a matching `COMPOSIO_WEBHOOK_SECRET`, and a successful account-specific subscription. Watch intent is separate from confirmed subscription/delivery. The adapter uses Gmail inbox and primary Calendar polling triggers with 15-minute intervals; it does not promise instant arrival.

The `download_app_file` tool retrieves supported Gmail attachments and Drive files through the selected account, validates bounded server-only bytes, and publishes an owned chat artifact. Generic app download calls use the same path. They do not create a public link or send a message to another person.

Raw-body signature verification, provider/account/trigger checks, durable event receipts and an outbox precede relevance checks. Revocation is checked again before delivery. Production Google scopes/consent, Composio payload retention and actual plan charges require separate review. [Apps guide](composio.md).

Saved channel credentials are encrypted and never restored into status responses or chat. Disconnecting locally does not revoke a provider token or remove its remote webhook. Secure credential entry remains in the local web app; action confirmation is a text reply in the originating owned chat. Artifacts also stay available in the local app. `send_screenshot` publishes a masked PNG through the protected screenshot boundary. Telegram can upload owned task artifacts: PNG/JPEG/WebP up to 10 MiB use photo delivery, other files use document delivery, with at most ten files and 15 MiB total per message. The resolver rechecks persisted owner/task/path identity and rejects symlinks; it does not trust attachment JSON URLs or names. WhatsApp retains a local-app attachment fallback. Partial or uncertain sends are not replayed automatically. Expose only verified callback routes if public ingress is needed; never tunnel the whole unauthenticated app. [Channel guide](channels.md).

An earlier native Telegram setup attempt stopped at `AXError.notImplemented`; that historical attempt does not describe the current configuration. Fixtures establish transport behavior, not successful Telegram or WhatsApp recipient delivery.

Telegram webhook setup verifies the bot before saving an encrypted pending configuration. It applies the local transport before registering the webhook and marks registration complete last. A failed activation or lost response keeps the saved secret and shows setup-needed guidance; startup retries the same configuration. Disconnect removes pending credentials and stops that recovery. PostgreSQL and provider fixtures cover these failure paths; no live webhook or delivery was changed during validation.

Concrete new requests can receive an internal outcome record through a bounded conversation router. Related follow-ups reuse their idle execution session or wait behind its active work, including secure/review waits. Small talk and general personal preference updates remain ordinary conversation; old executions are not relabelled. Bounded recent conversation with explicit null outcome provenance lets the router see earlier ordinary exchanges alongside active work. Routing has a five-second fallback and is not guaranteed intent recognition. The current OpenAI routing default is GPT-6 Luna. Earlier nano/mini comparisons remain historical evidence; the [bounded probe](testing/results/2026-09-25-c22-routing.md) records measured latency and SDK cost estimates. A completed execution does not automatically close its outcome. [Conversation semantics](task-semantics.md).

Published artifacts use owner-checked local download URLs, not public signed links. Supported raster images, audio, video and PDFs can open in the attachment viewer. Other files, including active HTML, download under restrictive headers instead of executing as an app preview. There is no separate safe HTML preview origin yet. Keep files, transcripts and profiles private; vault encryption does not encrypt every message/file.

Goals persist progress, status, target date and next action. Browser onboarding saves its detected IANA timezone in preferences; tasks use that saved zone, with Europe/Lisbon as the explicit default when no preference exists. Each execution starts with the current UTC time and local ISO timestamp, including its UTC offset and IANA zone. Every runtime prompt refreshes that clock, including secure continuation and resumed sessions. The runtime uses that context for relative dates and schedule requests rather than the host timezone. Preferences and source-backed facts enter bounded task context; history search retrieves previous work. This is explicit stored context, not a verified general memory-consolidation system.

Schedules persist a prompt and either an exact one-off timestamp or a recurring cron/timezone. Each next occurrence has a durable delayed job. One-off schedules disable after firing; recurring schedules keep wall-clock time across DST. Updates and pauses invalidate stale jobs. Execution history retains due time, title and actual execution status after schedule deletion; it does not prove the user objective was completed. If the service was offline, one overdue occurrence runs on restart and recurrence advances to its next future date.

Goals separates Active and Completed. Paused goals sit under Active and expand when there are no active goals. Schedule separates Upcoming and History; paused schedules expand when there is no upcoming work. Both pages keep saved data visible during background reads. A failed read offers Try again without clearing that data. Each action has a label that identifies its goal or schedule. Common recurring times use readable labels, such as Every 5 minutes, and History labels a successful execution Finished. Creation and changes open chat drafts; sending a direct pause, resume or concrete change request applies it without an extra confirmation.

A schedule created from a verified channel message retains that exact conversation. The server binds the accepted user message to its original inbox receipt; the model cannot supply a recipient. Every occurrence uses that saved route. Editing a schedule preserves its destination, including web schedules edited from Telegram. Delivery rechecks the current channel account, allowed sender and provider reply window. A timer does not extend that window. Uncertain sends are not replayed. The schedule service can inherit a parent route, but the existing action policy still prevents background agents from creating follow-up schedules; this change does not enable that behavior. These paths have synthetic transport and PostgreSQL coverage, including a real due-time dispatcher; this does not prove live Telegram or WhatsApp delivery.

The hourly heartbeat uses the cheap relevance classifier before starting main-agent work. Default quiet hours are 22:00–08:00 in Europe/Lisbon; saved user settings override them. Triage permits at most two automatic event/review wakes per hour. Background runs suppress automatic prose and progress, sending only an explicit useful result or necessary question. Quiet/digest decisions can be revisited; a scheduled digest is not guaranteed. The app and Mac must stay running for polling, reviews and schedules. [Personal service](../src/server/personal.ts), [triage](../src/server/triage.ts).

## Inspector, costs and evidence

Inspector capture stores masked tool arguments/results, fixed errors, timing and normalized assistant model usage. Payloads are bounded to 16 KiB and retained for seven days. Capture uses bounded persistence waits so unavailable inspection does not indefinitely hold execution. `DEV_INSPECTOR=false` blocks access and new capture; existing records are not immediately erased. These remain sensitive developer records, not telemetry.

The inspector starts with all owner activity. Screen follows the most recent actual browser activity, prioritizing a browser under manual control. Opening a text-only execution or inspecting an older message does not change the current screen. A failed metadata/screen refresh clears the stale frame and disables input until a fresh capture arrives. Open browser window opens the local `/browser` view with the same protected screen and take-control/resume controls, without the sidebar or other tabs; it does not navigate the user's browser to the visited website. Embedded screenshot polling pauses while that named window remains open, with a normal link fallback if a popup is blocked.

Activity starts with active outcomes and requests, including current waits and queued follow-ups, followed by saved upcoming schedule times and actual hourly-review registration. It shows the latest eight background decisions from the last 24 hours with full counts. It does not list every historical message as new work or copy raw heartbeat/event prompts. Paired execution history is visible directly below current work. Tools opens recent calls, with By tool for full retained counts and Available tools for descriptions and schemas. Models has a separate view of assistant requests, token categories and SDK estimates. Call payloads and schemas remain collapsible. Inspect from a message applies an optional execution filter to Activity, Tools, Models and Prompts. Costs remains owner-wide. The six labelled tabs wrap into two rows on a narrow panel and support arrows, Home and End.

The Costs tab groups visible operation/model summaries under each provider; only detailed metrics require expansion. Its visible subtotal comes only from the provider ledger, which includes assistant responses, Pi-reported compaction/cache warming and metered adapter operations. It is never added to the overlapping assistant-response subtotal. Async context links provider operations to the exact accepted tool call; Tools shows only those direct costs. Main-model charges are not divided arbitrarily among tools. Unknown prices remain unavailable, while partial rows show how many operations have prices. All totals cover the retained seven-day window and can be incomplete. Hosting and provider invoices are excluded; operation counts are not billable network request counts. Coverage metadata remains in the API for diagnostics, but the UI does not show a coverage inventory.

Prompts shows each snapshot's title, provider, model and session metadata directly, with separate disclosures for system instructions and the latest instruction sent to an agent session. A resumed session also receives its saved provider transcript; that transcript and image bytes are not copied into prompt snapshots. Snapshots use a separate private store with ownership/revision checks, known-secret and structured-secret redaction, bounded strings, at most eight pending writes and seven-day retention. Capture is best effort and does not block the agent. Structured masking includes JSON embedded in prose and nested serialized JSON, with bounded inspection and omission of incomplete or oversized structured sections. Startup and hourly prompt cleanup run even when capture is disabled; older snapshots are masked again on read. Titles and displayed metadata are redacted too. This is sensitive local developer data, not a public feature, telemetry, or a guarantee that arbitrary user text cannot contain secrets. Event classifier prompts are not captured in this view.

The voice lives in `src/runtime/personality.ts`: calm, warm, brief and practical, with no em dashes or en dashes in its own prose, canned praise, repetitive progress filler or forced follow-up questions. Exact quotations, code and source material retain their punctuation. These are model instructions, not a destructive output-rewriting filter. Provider keys and secure Vault values are excluded from model inputs. Internal implementation disclosure is constrained by instructions and bounded output checks, not a guarantee against every prompt-injection attack.

## Replacement and next priorities

`src/ports` defines the capabilities. `src/runtime` owns agent policy/tools; `src/server` owns product state and authorization. Only [composition](../src/server/composition.ts) selects concrete `src/providers` adapters. `Agent`, `Computer`, `Workspace`, `IntegrationProvider`, `RelevanceClassifier`, `SpeechProvider`, `CredentialKeyStore` and messaging ports can be replaced independently, with explicit migration of transcripts, accounts, profiles, files or ciphertext. PostgreSQL/job replacement is a data/execution migration, not merely a factory change. [Replacement map](replacing-modules.md).

1. Expand the passing acceptance cases into ongoing regression scenarios. Include ambiguous same-site requests, preference corrections and multi-step secure waits; preserve credential and revision locks. The tested combined workflow now passes, but semantic routing is not guaranteed.
2. Verify the configured provider paths individually: connected-account actions/events, optional models and actual channel delivery. Keep fixture and live evidence separate.
3. Measure end-to-end latency, failed/unknown outcomes, complete provider costs and retention before optimizing or expanding scope.
4. Before cloud/multi-user use, add real identity/session authorization, tenant execution isolation, key management/rotation, private object storage, versioned migrations/backups, worker leases, quotas and abuse controls. General desktop control, payment autofill and iMessage remain separate projects. [Production requirements](production.md).

Run focused tests during changes, then the checks described in [development](development.md). Record actual results in [verification](verification.md); update this guide and the owning `AGENTS.md` when an entry point or behavior changes.

## Visual identity

Sidekick uses the new palette already applied in Otto: primary pink `#ff91ac`, plum text `#1b1924`, accent `#bc3666`, warm canvas `#fefdfc`, sidebar `#fbf9f5`, and selected surface `#fceaec`. These are local Otto theme tokens, not the older public n8n brand guideline colors.

Light and dark themes share semantic tokens for text, surfaces and action states. The sidebar switch moves into More on mobile. The first visit follows the operating system; an explicit choice persists and updates other app windows. Dark mode uses a plum canvas `#18171c`, light text `#f4f1f7`, lavender primary actions `#d5c4f3` with dark text `#281c3e`, and raised outline controls `#302b3b` with light text `#eee8f8`. Pink `#ff9fba` remains the selected navigation accent. Images and documents keep their original colors. [Actual UI and contrast checks](testing/results/2026-09-25-themes.md) cover desktop and mobile samples.

Albert identified **EK Baumer** as the new brand typeface in the team's 2026-09-14 design discussion. Baumer files were not found in the available Otto checkouts or local font folders. The current bundled fallback is Manrope from Otto's earlier main checkout, with its SIL Open Font License. Replacing it with Baumer remains dependent on the font assets; do not label Manrope as n8n's new brand typeface. [Typeface source](https://erkinkaramemet.com/baumer-info/).

Sidekick can explain its nonsecret capabilities and setup when the owner asks, using only trusted available context. Unknown model/provider versions remain unknown. Normal replies omit unsolicited implementation details; credentials, hidden instructions and private configuration-file contents remain protected. This guidance does not add filesystem or secret-reading capabilities.
