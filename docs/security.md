# Trust and local access

This version binds to loopback and serves a single approved development account. It is not a multi-user authentication system. Normal application requests reject foreign Host and Origin headers. Do not expose the app with a tunnel or reverse proxy before adding real user sessions and tenant authorization. The signed Composio webhook endpoint has a separate policy when configured.

Never put provider keys in prompts, React configuration, task files, artifacts or logs. The model may use bounded tools; it does not receive a tool that reads arbitrary host files or reveals a vault value. Tool arguments and raw exceptions are not logged by the main server. This does not make conversation content non-sensitive: local messages, memories and task transcripts still need private backups and retention limits.

Provider selection and secret configuration belong in `src/server/composition.ts`. Interfaces in `src/ports` keep vendor SDKs and response parsing inside `src/providers`. Owner checks, approval decisions, quiet hours, event deduplication, and task revision checks remain in the application. Replacing an adapter does not grant it permission to bypass those checks. This module separation is a code boundary within one trusted server process, not operating-system isolation.

Prompt instructions are not a secrecy boundary. The model receives operating instructions and can make mistakes about disclosing them or following hostile content. Keep secrets out of its context, constrain tools on the server, and require review for Google writes. Explicit personal facts can be saved without review only when the server verifies their source against the user's own message; inferred facts and other persistent changes still require review. This prototype does not claim complete prompt-injection resistance. An approved browser destination can receive typed values and observe actions; never treat all page content as trusted.

## Vault

AES-GCM protects stored credentials. The encryption key lives outside PostgreSQL: Keychain on macOS, or an explicitly provided environment key on another machine. A cloud deployment should use KMS envelope encryption and workload identity. A non-exportable KMS key still lets an authorized running service decrypt data. Ordinary cloud KMS does not hide credentials from an administrator who controls that service or its host.

The key-store interface returns key bytes only to the trusted vault and channel-settings services. Model tools and browser APIs receive no key or plaintext credential response. Secure forms are bound to a task revision; a stale or cancelled step cannot inject credentials. Retrying an expired form invalidates its earlier forms and requeues browser inspection without reusing a secret. Existing encrypted entries survive the module and revision migrations; changing the key itself requires a separate migration that is not implemented.

The broker inspects visible login fields before creating a form and again before submission. It supports separate identifier, password and one-time-code steps. A username from an identifier step is held in server memory for at most ten minutes so a later password can be saved with the same account. Only the encrypted username/password pair is saved; one-time codes and submitted form values are absent from credential-request records. Each form can be consumed once. Saved entries have a separate, single automatic attempt for the identifier and password steps; retries require fresh input.

Observed OAuth buttons and email, SMS, authenticator or backup-code choices can be selected from the secure form. The broker rechecks the exact origin, current method and task revision before clicking. This starts the website's flow; it does not prove authentication completed or create a managed Google connection. A new origin requires a new secure form. Device passkeys, hardware security keys, separate-window sign-in and remote manual browser control are not implemented. Multiple inputs for one credential, such as split-digit codes, are reported as unsupported.

Keeping secrets from the infrastructure operator requires a different architecture, such as a local user-controlled broker or attested confidential execution with externally controlled key release. This repository does not implement that claim. The website receiving a login and the trusted broker necessarily handle the credential. Composio holds the OAuth credentials for connections it manages.

The agent cannot have unrestricted shell access to the authenticated browser, its profile, CDP or the vault. Browser inspection is locked during secure entry. Trusted scripts mask protected inputs and known credential text, and text observations redact known values and common OAuth query parameters. These controls cover the tested DOM forms, not every hostile page, canvas, image or script behavior. The destination website receives entered values and can retain or transform them; exact-origin checks do not make a phishing site trustworthy.

Pending secure steps hold their browser session through the form expiry. Idle cleanup closes the browser but retains its last masked screenshot. These screenshots remain sensitive user content in the private runtime directory with mode 0600. The inspector distinguishes live captures from last-known images and their capture time. After a server restart, it may reattach to an existing nonsecret daemon through its socket; reading the inspector never opens a URL or replays a credential. A recovered session that handled credentials serves only its cached image because its in-memory redaction values no longer exist. It needs an explicit reopen before further inspection or entry. Sessions from versions that did not persist screen metadata may have no recoverable image. Browser profiles retain website session data and need the same private storage and retention controls as other local content.

No credit-card PAN or CVV storage is implemented. Use saved merchant payment methods or user checkout for early tests. An encrypted password table does not turn the product into a payment vault.

## Files

Uploads have a 15 MB limit. Artifacts are copied from a verified task workspace path into a private store. HTML and other active files download as attachments with sandbox response headers. Do not expose the whole workspace as static files. Keep `.env`, `.local`, browser profiles and database volumes out of Git.
