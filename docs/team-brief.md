## What it does

Sidekick is a personal assistant built around one chat. It can navigate websites, use connected apps, create and return files, retain personal context, track goals and run scheduled work. Internal execution sessions group related requests; a follow-up can continue the same work instead of becoming a separate visible task. Hosted users sign in with Google, connect their own accounts and use operator-configured providers. [Product and system guide](system-guide.md).

Implemented surfaces include:

- **Browser and files:** per-task Chromium profiles in a trusted Linux container, screenshots in chat, separate Linux command execution and owned artifacts. Images, audio, video and PDFs share a compact preview before and after sending. Computer views and direct controls are developer-only in hosted mode; ordinary users work through chat.
- **Account and settings:** Google avatar, profile, light/dark/system appearance, timezone and quiet hours. Settings uses vertical tabs and theme previews; appearance is also available from the account menu. Cmd/Ctrl+, opens settings. Hosted preferences persist per account. Onboarding opens each app's consent directly and returns to the same screen with refreshed status.
- **Apps:** Gmail, Calendar, Drive, Sheets, Docs, Slack and Notion through Composio, with multiple accounts per service. Known ordinary actions can use a clear user instruction; destructive or unmatched actions ask a specific question in chat. A draft request does not authorize sending. Account bindings and the original user instruction are checked by the server.
- **Vault:** named website logins, exact-origin account selection and staged identifier/password entry through one private form. A verification code uses a narrow trusted lookup in the exact matching connected Gmail inbox, or a chat reply that is masked before local history and model processing. The agent can continue the original browser task after submission. Logins and encrypted payment cards open directly for editing; saved passwords, card numbers and optional CVC/CVV use explicit reveal/copy/change controls. Deletion is confirmed inside the modal. Payment autofill is not implemented.
- **Personal work:** saved facts, preferences, goals and one-off or recurring schedules. Goals has Active and Completed views; Schedule has Upcoming and execution History. Validated local plan changes can run without a second confirmation; the model must distinguish review-only requests from intended changes. Both pages offer confirmed deletion. Each model prompt receives the current local date/time, UTC offset and saved timezone, defaulting to Europe/Lisbon.
- **Channels:** one allowlisted sender per configured Telegram or WhatsApp account, with hosted account ownership and claim checks. Telegram supports owned image/file delivery; WhatsApp supports text in its reply window and an in-app attachment fallback. Live recipient delivery remains an acceptance gate.
- **Inspector:** current browser, active work, tool counts and actual calls, provider-grouped usage/cost estimates and private prompt snapshots. Hosted access and capture require developer authorization and enabled Inspector configuration. Unknown prices and failed recordings can make totals incomplete; these are not invoices.

Mobile keeps Chat central, with navigation, account/settings and theme choices in a top-right menu. Desktop retains the collapsible sidebar and avatar menu. Enabled developer tools remain separate from ordinary account navigation. Apps retains its connected-account management page; onboarding omits account identifiers and additional-account controls. [Web implementation](../src/web/AGENTS.md).

## How it works

In ordinary local mode, one Node process serves React/Fastify, task workers, the scheduler, background reviews and channel processing. Hosted mode adds a Google-authenticated gateway and one leased Node runtime per user, with a restricted PostgreSQL login and private app/jobs schemas. Cloudflare places the gateway and tenants behind a public Worker; private R2 access is owner- and generation-bound. The selected E2B adapter prepares one owner sandbox during authenticated onboarding. Browser and workspace share it under separate Linux users with a checked private-browser boundary. Authentication/control credentials stay in the gateway, and computers receive no service keys. [Architecture](architecture.md).

PostgreSQL and pg-boss persist messages, execution revisions, waits, jobs and delivery records. Pi runs the model/tool loop. Provider adapters sit behind capability interfaces; only server composition selects models, integrations, computers and storage at startup. Users connect accounts without choosing a computer provider or supplying operator API keys. Jan's existing paid Cloudflare plan hosts the server; E2B computer access and billing are separate. Docker supports ordinary local mode, and the earlier Cloudflare computer adapter remains available with its existing recovery records. [Composition](../src/server/composition.ts), [replacement guide](replacing-modules.md).

The ordinary local Docker path separates the trusted browser from the Linux shell, with a private browser volume and fixed execution bridges. It still has one owner's workspace and is not a multi-user boundary. Hosted runtime identity is immutable; signed requests, expiring leases and confirmed provider pause/stop fence replacement generations. E2B reconnects the same owner allocation only after readiness checks; live persistence remains unverified. The optional Cloudflare computer adapter preserves acknowledged workspace files and clean browser profile checkpoints, not live page memory or arbitrary website sessions. Unknown actions remain fenced. Vault and channel secrets use authenticated encryption; other messages, files and transcripts are sensitive data, not automatically encrypted by Vault. [Security](security.md).

Production CI/CD is implemented: required CI gates the main-branch deployment workflow, which builds immutable images, drains accepted work, verifies provider-specific pause/stop evidence and checks rollout/smoke results before reopening admission. The local Wrangler launcher reuses signed preparation for checkpoint-safe shutdown and restart. Manual publication and the automatic main-to-production workflow have both passed, including verification of the exact merged release and two-account file persistence afterward. The selected E2B journey remains an acceptance gate. [Production requirements](production.md), [Cloudflare runbook](../deployment/cloudflare/README.md).

## Local setup

Install Node.js 24.21.0 or newer, start Docker Desktop and run `npm run dev`. The launcher prepares dependencies and three containers: PostgreSQL, workspace and browser. Chromium comes from the browser image, with no host installation. The web app opens on loopback port 4310. Select `LLM_PROVIDER` and add its OpenAI or Anthropic key to ignored `.env`; Composio is optional for Apps. macOS uses Keychain; other hosts need `SIDEKICK_VAULT_KEY`. Channel setup is optional. [Setup](../README.md), [configuration](../.env.example).

This ordinary local mode has no app login and must remain private on loopback. Schedules, polling and reviews require its machine and app to remain running.

To test the selected hosted path locally, prepare separate development Google, PostgreSQL, integration and E2B configuration, including `COMPUTER_PROVIDER=e2b` and `E2B_COMPUTER_TEMPLATE`, then run `node scripts/start-hosted.mjs --env <private-development-env>`. It runs the gateway and tenant processes on port 4330 with development E2B computers, without a Cloudflare deployment. The optional `COMPUTER_PROVIDER=cloudflare` path starts local Wrangler, Docker containers and R2 emulation. Production projects and keys stay separate. Use graceful shutdown before editing watched source or rebuilding. [Hosted development](development.md), [environment example](../deployment/hosted.env.example).

## Priorities and limits

1. **Keep acceptance evidence current.** Expand regression coverage for ambiguous follow-ups, memory corrections and multi-step waits. Routing and action-intent recognition are bounded model/policy decisions, not general reliability guarantees. Automatic outcome completion is not implemented.
2. **Verify providers individually.** Synthetic consent, app reads and messaging transports do not prove external OAuth, event delivery or recipient delivery. Real website authentication remains provider-dependent; a reachable login page is not a successful login.
3. **Measure complete behavior and cost.** Track end-to-end time, unknown action outcomes, missing usage records and actual provider bills. Background reviews are limited and do not guarantee a digest. Background agents cannot currently create follow-up schedules without direct user authorization.
4. **Complete hosted release acceptance.** Authentication, tenant isolation, private storage, leases and controlled deployment are implemented. Complete remaining integration consent/events, Telegram delivery, deployed recovery and production account checks; verify backups, key recovery, costs and operational limits before broader access. General desktop control, iMessage and card autofill remain missing. [Production requirements](production.md).
