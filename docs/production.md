The repository includes Google login, account settings, isolated per-user Node runtimes, private tenant SQL roles, a Cloudflare container adapter and production CI/CD. This is a bounded pilot implementation. Automated fixtures and local process tests do not establish a working public deployment or live provider delivery; record those checks separately before sharing a production signup link.

## Selected E2B deployment shape

```text
Browser / verified webhook
            |
Public Cloudflare Worker + static web assets
            |
Private Node gateway: Google sessions, accounts, tenant provisioning
            |
One private Node container per user, signed requests and expiring lease
            |
Private PostgreSQL role + app/jobs schemas
            |
One owner E2B computer: browser + files + commands     Private R2 artifacts/transcripts
```

The gateway authenticates the session before selecting an owner. Each tenant process has an immutable owner, its own SSE emitter and task workers, its own PostgreSQL login and application/jobs schemas, and a separate working directory. Schema permissions isolate child tables even where they have no owner column. Tenant roles cannot read another tenant or the control/auth schemas, create roles, or switch to another tenant role. Provisioning never adopts unrelated existing roles or schemas.

Control/auth database credentials, Google login secrets and the tenant derivation master key stay in the gateway. Actors receive derived database/vault credentials, signed-runtime identity and selected provider credentials. The E2B sandbox receives no model, integration or database keys. Its combined template runs the browser as `otto-browser` and shell commands as `node`, with private profiles/control sockets and a root-owned guard checked after create/resume. These same-VM protections are implemented and fixture-tested, not yet live-provider proof. Public ingress does not expose actor bootstrap or internal channel claims; trusted tenant identity and generation determine private storage and stop acknowledgements.

The pilot admits eight users and keeps one gateway plus up to eight tenant containers active. The selected E2B path has one durable owner allocation shared by browser and workspace; it pauses without replacing its resource ID. Minute Cron and gateway recovery restore registered runtimes. Actors require signed SQL-backed lease renewal and self-fence on expiry. Replacement requires confirmed application termination and acknowledged computer pause; unknown outcomes remain fenced. Increase admission, provider quotas, database connections and budgets together. Jan's existing Cloudflare plan covers application hosting under its normal usage charges; E2B has separate account/billing requirements. The optional Cloudflare computer configuration retains eight browser and eight workspace slots.

## Operator configuration

Use distinct development and production Workers, Durable Object namespaces, private EU R2 buckets, PostgreSQL databases, Composio projects/auth configs and Google OAuth clients. E2B keys/templates must also remain separate if that provider is selected. PostgreSQL initialization changes default public grants, so use a dedicated Otto database with a provisioner allowed to create login roles and schemas. Keep that credential out of actors and task computers.

| Configuration                                                                             | Purpose                                                            |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `OTTO_MODE=gateway`, `OTTO_ENVIRONMENT`, `OTTO_PUBLIC_URL`                                | Hosted entrypoint and fixed application origin                     |
| `OTTO_PRIVACY_NOTICE_FILE`                                                                | Gateway path to the reviewed public Markdown privacy notice        |
| `DATABASE_URL`                                                                            | Dedicated control/auth database and tenant provisioning connection |
| `OTTO_MASTER_KEY`                                                                         | Stable 32-byte key for tenant database/runtime/vault derivation    |
| `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`                          | Login sessions and Google OAuth                                    |
| `OTTO_MAX_USERS`                                                                          | Atomic admission limit, default eight                              |
| `OTTO_DEVELOPER_IDS`                                                                      | Account UUIDs authorized for developer/computer views              |
| `COMPUTER_PROVIDER=cloudflare`                                                            | Optional separate Cloudflare browser/workspace roles               |
| `COMPUTER_PROVIDER=e2b`, `E2B_API_KEY`, `E2B_COMPUTER_TEMPLATE`                           | Selected owner computer, combining browser, files and commands     |
| `OBJECT_STORAGE_PROVIDER=http`, `OBJECT_STORAGE_ENDPOINT=http://otto.storage/v1/objects/` | Private Cloudflare storage broker                                  |
| Model keys/settings and `COMPOSIO_*`                                                      | Server-owned providers and enabled integrations                    |

Users choose which accounts to connect; startup configuration selects computer/model providers. Onboarding starts authenticated preparation while integrations stay usable. Completion is also guarded server-side; no client request can mark setup complete before preparation succeeds. Repeated preparation reuses the same allocation. Legacy split-template settings and retained split allocation rows require explicit operator migration, never automatic adoption. The Google callback origin must match the deployed HTTPS origin. Profile, avatar and settings belong to the authenticated account; appearance is also accessible from the account menu. Hosted Inspector capture requires both `DEV_INSPECTOR=true` and an owner UUID in `OTTO_DEVELOPER_IDS`; ordinary accounts do not persist Inspector prompts or tool payloads.

The routing diagnostic contract retains only strict taskless/tool-less `relevance/conversation_route` failure/cancellation metadata with Inspector disabled: a fixed code, optional HTTP status and bounded model/timing/usage fields. It excludes prompts, outputs, raw errors, causes and keys; private recording is nonblocking, capped at 128 pending writes and retained for seven days. Inspector access remains gated. [The dated investigation](testing/results/2026-09-28-routing-diagnostics.md) records the production refusal and the separate validation/deployment status of this diagnostic change.

Cloudflare stores the gateway configuration as a compact JSON `GATEWAY_ENV` secret, limited to 5 KiB. Deployment validates origin/environment, injects the release SHA and keeps keys out of build arguments and web assets. The [Cloudflare runbook](../deployment/cloudflare/README.md) lists resources, token scopes, CI secrets, private RPC and deployment commands.

Self-hosting can use the Node gateway's local per-user process transport and a compatible PostgreSQL service with E2B computers, or the full Cloudflare path. `scripts/start-hosted.mjs` selects local Wrangler/Docker/R2 emulation when `COMPUTER_PROVIDER=cloudflare`; the E2B/process path stores private objects in each tenant's PostgreSQL schema. The optional filesystem adapter requires a durable private volume and manual stale-lock recovery after an interrupted writer. Computer/storage ports keep provider details outside product logic. Use development projects and disposable data locally. Local process isolation assumes a trusted host; never expose the single-owner `local` mode publicly. See [replacing modules](replacing-modules.md) and [development](development.md).

## Privacy and Google sign-in

Before sharing a hosted signup link, customize the [operator privacy template](privacy-notice-template.md) into `public/privacy-notice.md`. Name the actual operator/contact, enabled providers and data practices, and define a workable retention/deletion process. Do not publish placeholders or invent guarantees about training, human access, region or automatic deletion. Full account deletion is currently an operator procedure across authentication, PostgreSQL, object storage and provider computers; app disconnect and conversation reset retain historical data.

Set `OTTO_PRIVACY_NOTICE_FILE=public/privacy-notice.md` for the local Node process path. The build copies the public file into `dist/web/privacy-notice.md`; use that path for both local and deployed Cloudflare gateways. The gateway reads it at startup with a 128 KiB byte limit and 32,000-character limit, serves anonymous `/api/privacy`, and does not forward it to tenants. The raw Markdown is also intentionally public. Only the file path goes into `GATEWAY_ENV`, preserving its 5 KiB total budget. An omitted setting permits deployment without a notice, so readiness must be checked operationally. A configured unreadable or invalid file fails startup.

Verify `/privacy` while signed out on the actual HTTPS origin, confirm that the reviewed notice is displayed, and set that URL as the Google OAuth client's privacy-policy URL before sharing. Repeat this after a notice change or release. A successful login is not evidence that the policy page or OAuth branding configuration is complete.

Google rules checked **2026-09-27**:

- Otto's own Google client requests only `openid`, `email` and `profile`. For an External app in Testing, requests limited to these identity scopes do not require a test-user listing, do not show the testing warning, and are exempt from the seven-day testing authorization and refresh-token expiry. Additional scopes remove this exception. Workspace or account security policies can still restrict access. This does not change Otto's own seven-day session expiry. [Audience rules](https://support.google.com/cloud/answer/15549945?hl=en), [refresh-token expiry](https://developers.google.com/identity/protocols/oauth2#expiration).
- Google's personal-use definition includes fewer than 100 users who are all personally known to the developer. A pilot meeting that definition can use the verification exception; an open invitation or unrestricted public signup must not assume it. Publishing state, scope verification and brand verification are separate: authentication-only apps released for public production must complete brand verification. That review includes homepage, privacy-policy links and domain ownership. [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), [verification exceptions and requirements](https://developers.google.com/identity/verification/authentication-verification), [authentication production policy](https://developers.google.com/identity/verification/authentication-policy-compliance).
- The verification exception does not waive accurate privacy disclosures. Google requires a published policy describing Google-data access, use, storage and sharing, with the policy URL included in the OAuth configuration when publicly available. [Google API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy).

Keep basic login separate from Gmail, Calendar and other app grants managed by Composio. Their additional scopes have their own consent and verification requirements; neither basic login success nor the identity-only exception validates those connections. Live production signup, logout and account isolation still need their own acceptance checks.

## Durability and external actions

For an authorized reset, follow [Resetting an environment](environment-reset.md). Deleting authentication rows or truncating the database alone leaves object storage, computer state and remote integration connections behind. Keep admission closed until all selected user resources have been removed and verified.

Tasks, jobs, schedules, event inbox/outbox and ownership live in PostgreSQL. Artifacts and Pi checkpoints use bounded private object storage with conditional writes. A stale checkpoint writer fails; a saved pre-action journal without a confirmed result prevents automatic replay. Failed conditional cleanup can leave a private orphan for reconciliation rather than delete a newer object. Cloudflare container disks are ephemeral working space.

The optional Cloudflare computer provider preserves separate owner/role filesystem checkpoints in R2. The browser archive contains its private profile directory; the workspace archive includes task files and installed CLI tools. Archives are limited to 256 MiB, individual files to 64 MiB and entries to 20,000 including the root. SHA checks and atomic restoration preserve file modes and safe internal relative symlinks. Workspace terminal completion waits for process-group drain and a durable checkpoint. Browser idle shutdown requires quiescence; active holds and native sign-in may decline it. Normal stop may close browser sessions before checkpointing. These are file snapshots, not preservation of a live DOM, process memory or an unfinished external action.

Database idempotency does not make external writes or browser actions exactly once. A provider may accept an action before its acknowledgement is lost. Preserve uncertain outcomes and reconcile them rather than silently replaying. Computer resources are owner-bound and leased; unknown termination, dirty recovery, missing command acknowledgement or failed checkpoint publication fences further execution. The selected E2B browser and shell share one resource but retain separate capability and Linux-user boundaries. Do not clear that state or restore an older checkpoint to bypass uncertainty. Fixtures do not prove that a real website permits automation.

The selected workspace can execute arbitrary commands and reach its configured network. It receives no trusted provider keys, host Docker socket or authenticated browser profile. These separations do not prevent every prompt-injection outcome or replace provider network controls, quotas and monitoring. A browser screenshot is not a native operating-system desktop.

## Integrations and messaging

App connections use Composio authorization and owned callback attempts. Gmail/Calendar subscriptions, signatures, deduplication and owner routing need a real production event test; enabling a preference does not establish delivery. Keep development and production Composio credentials separate. Check the managed OAuth application's actual consent and sensitive/restricted-scope status; these app grants are separate from Otto's identity-only Google login. [Google OAuth production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).

Telegram setup verifies the bot identity, claims it for one Otto account, encrypts its credentials and uses an owner-bound webhook route. Another user cannot claim the same verified bot. The current form requires the user's numeric Telegram sender ID; one-time deep-link pairing and a verified test challenge are not implemented. Sender binding, webhook authentication and owned routing remain required. Test registration, receipt, a reply, disconnect and duplicate delivery in production. Uncertain remote webhook state or token revocation requires provider-side reconciliation. Local polling and synthetic fixtures are separate evidence.

WhatsApp needs its own current eligibility, pricing, account and template review; a working adapter is not worldwide production availability. Preserve reply-window limits, channel identity, account-bound approvals and uncertain-send behavior described in [channels](channels.md).

## CI/CD and rollback

CI checks root types/architecture/formatting, the full PostgreSQL fixture suite, client build, Cloudflare types/fixtures, both environment bundles and all three amd64 role images. Image checks cover unprivileged users, key/filesystem boundaries, fixed helpers, readiness and graceful shutdown. Production follows successful CI for the current `main` revision, inside the GitHub `production` environment. Configure branch/environment protection so reviewed `main` code alone receives production secrets.

Deployment rebuilds the runtime, browser and workspace images from the exact CI-validated commit and rechecks current `main` immediately before publication. It validates all required classes and hosted providers, pre-pushes the selected images and resolves immutable digests. A purpose-specific HMAC derived from the gateway master key then closes a durable admission barrier. Existing tenant work drains naturally while lease renewals continue; each exact generation needs an acknowledged tenant drain, confirmed termination and provider-specific computer proof before Worker activation. E2B requires acknowledged non-forced pause of the combined computer; the optional Cloudflare computer provider requires both clean role checkpoints and confirmed stop. Active holds, uncertainty, failed cleanup or an expired deadline block deployment. No deployment step force-cancels accepted work or clears a fence.

Worker code, image references and `GATEWAY_ENV` publish together through `wrangler deploy --secrets-file`. Worker activation and image replacement remain separate Cloudflare operations, so admission stays closed until every selected application reports its expected image with no active/conflicting rollout and the gateway smoke passes. Smoke verifies the exact image release, anonymous session/state boundaries, private-route denial and foreign-origin POST rejection. CI does not log in to Google, connect apps or send messages. The first deployment additionally requires an explicitly absent Worker, no matching container applications and an empty tenant registry; its managed startup remains closed until verification finishes.

Pre-activation abort uses the same deployment identity and resumes only safe untouched tenants. After a gateway restart, recovery requires read-only proof that every registered tenant and its selected computer resources are safely stopped or paused, including settled platform startup attempts and durable provider proof. Failed or unknown evidence remains closed. The [Cloudflare runbook](../deployment/cloudflare/README.md#rollout-and-verification) provides `recover.mjs` status/abort/complete commands; completion preserves the interrupted nonce and target, verifies all image rollouts and reruns smoke. There is no automatic rollback or forced recovery.

Before any rollback, inspect the Worker, role images, leases and checkpoint states. Old code must support the current SQL schema, Durable Object classes, object/checkpoint format and key versions. Worker rollback does not restore PostgreSQL, R2, browser memory or external actions. Preserve prior images and keys; prefer a forward fix after incompatible state changes. Startup schema setup is not a tested reversible migration system. The deployment protocol is covered by automated fixtures; interrupted live Cloudflare rollout and recovery remain separate release checks.

Treat derivation and encrypted-data keys as recovery material. Replacing one without coordinated credential rotation or re-encryption can make accounts unavailable. Back up required keys separately from PostgreSQL/R2 and test restoration. Secret changes also require a controlled process restart because running containers retain startup values.
