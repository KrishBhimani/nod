# Vault

The vault stores encrypted website logins and payment cards in PostgreSQL. Website sign-in passes entered values to the trusted browser injection callback. Managed Google OAuth credentials belong to Composio, not this vault. Secure forms follow the current website step: an identifier, a password with an optional identifier, or a verification code. They can also offer observed sign-in and verification methods. Passwords, card numbers and codes do not enter chat or model context. Card autofill and TOTP seeds are not implemented.

## Encryption and setup

Each password record uses AES-256-GCM with a random 96-bit nonce. The authenticated data binds the ciphertext to its owner, exact website origin, and record ID. Moving ciphertext between records, accounts, or websites fails authentication. The private Vault list decrypts the full username so accounts are readable. The broker's login list and secure account choices retain only the item name, origin, identifier label, a short username hint and timestamps. Passwords never appear in either list.

Each entry has a user-defined name. Several entries can use the same origin without replacing each other. The manual Website domain field accepts `example.com` or `https://example.com` and stores the exact origin. It rejects paths, credentials, query strings and fragments. Subdomains, ports and schemes are not interchangeable. Secure links show the observed origin as fixed text; the user cannot redirect credential entry by changing the form.

Open a saved login in Vault to see its name, exact website origin and full username. The password starts hidden. Show password and Copy password make a separate owner-bound request; opening the details does not retrieve it. Copying a hidden password does not show it. Details and password responses use no-store headers and remain outside the page cache, local storage, chat, model context and Inspector records. Hiding the password, closing the view, leaving the page or moving away from the window clears the displayed password and rejects late requests. Copy places the selected value in the system clipboard; the app does not erase or manage clipboard history.

Open a login to edit its item name, website identifier or password. The website remains fixed to the saved exact origin. The saved password remains unchanged until Change password is selected. Its replacement field starts empty and requires a new value; Cancel change discards it. The existing password is never loaded into the editor. Cancel discards the form. Password input is cleared on submission or when the window is hidden. Successful saves update the private list, including the full username, without storing the password in its cache.

Updates recheck and lock the owned entry after key access, then decrypt and encrypt under the same owner/origin/record binding. A blank password preserves the latest saved value, including when another update completed while key access was pending. Missing entries, changed ownership, invalid fields, corrupt ciphertext and unavailable keys fail without changing the record. Update responses contain masked metadata only and use no-store headers. No agent capability exposes these updates.

The master key is outside PostgreSQL. On macOS, the app reads or creates the `dev.sidekick.vault` / `master-key-v1` generic-password item in the user's Keychain. Keychain access can require an OS prompt. It fails closed when the key is unavailable. On other systems, or when an explicit key is preferred, provide `SIDEKICK_VAULT_KEY` as exactly 32 random bytes encoded in base64. Do not commit it or put it in a browser-exposed variable. Back up the key separately from the database; losing it loses the saved passwords. Key rotation is not yet implemented.

The server composition selects `CredentialKeyStore` from `src/ports/key-store.ts`. The Keychain and environment adapters supply the key to the trusted vault and channel-settings services. `src/server/vault.ts` owns website credential encryption, owner and origin checks, database state, and HTTP routes. Replacing the key source must preserve the same key and ciphertext format; selecting a new random key does not migrate existing entries.

PostgreSQL encryption at rest alone does not isolate secrets from a running database or application. The app must decrypt passwords when it fills a website. This local design protects database copies; it is not protection against a compromised trusted server or another process with equivalent OS access. The current Keychain command-line bridge also briefly passes a generated key to the `security` process during creation. Strong isolation needs a distinct trusted broker identity and an agent environment that cannot read its memory, environment, browser profile, or key store. [PostgreSQL encryption options](https://www.postgresql.org/docs/current/encryption-options.html), [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services).

## Credential requests

The runtime supplies the task, requested website origin and kind, with optional selector hints. In the application, the broker inspects the current page through `Computer.inspectLogin` and derives the stage and selectors from its visible fields. It does not rely on model-supplied selectors. The vault binds this observed step to the owned task's current revision, issues a random 256-bit form token, stores only its hash, and expires it after ten minutes. Request records contain field and method metadata, not submitted values. The secure form is a local same-origin route. Its API responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

Only one submission can be in flight for a request. The broker rechecks the exact origin and observed stage before entry. It locks browser observations during entry, masks protected fields, fills only the required values, and waits briefly for a disabled Next button to become usable. Selectors target the top-level page; iframe login fields need a future broker flow. A staged identifier is bound to the task, owner, origin, revision and expiry. Its observed field label is normalized to plain text, limited to 80 characters and carried through the staged password save, including after restart. The saved label remains fixed during edits. New manual entries use Email for a valid email address and Username otherwise; older private details infer the same fallback without rewriting their ciphertext. Clients cannot set the label directly. Durable continuation encrypts this identifier with the same owner/origin/record binding; it is never included in request metadata or model output. Password entry requires a user-defined name and saves a separate encrypted username/password pair. Identifier-only entry does not create a password record.

A successful request is consumed, and a durable pending flag retries task continuation if scheduling fails. The resume callback must be idempotent. Failed entry returns a fixed error and requires freshly entered values; a pending request can be retried until expiry if the same stage remains available. After a server restart, an interrupted submission returns to pending, but the browser may need an explicit reopen before a new form can work. No submitted password, identifier or code is restored from a request record.

Submission requires the same task revision to be waiting for credentials. It locks that task during entry, so another request cannot change its revision. Cancelled tasks, stale forms, and consumed requests are rejected before injection. `POST /api/credential-requests/:id/retry` restarts an expired or failed current step through `retry(taskId, expectedRevision)`. It expires old forms and blocks automatic reuse for that task, owner, origin and credential kind. It does not decrypt a password or contact a provider. The task inspects the browser again and can issue a fresh secure form.

Migrations expire legacy forms without their original task revision or observed-field metadata. Their owners can restart a current waiting step through the same retry flow. Saved credential ciphertext and its owner/origin binding remain unchanged.

The broker-only `fillSaved()` method decrypts a selected record only for the matching owner and origin. The caller should use automatic reuse only when the account choice is unambiguous. A durable ledger permits one automatic identifier fill and one automatic password fill per task, owner and origin. It records each attempt before injection and blocks reuse after a form of that same kind has been completed. This lets a saved account pass through separate username and password pages without repeatedly submitting rejected credentials. Successful entry does not prove the website accepted the login. The agent must inspect the resulting page and request another user step when necessary.

When several entries match, the secure form offers their names and masked username hints. `POST /api/credential-requests/:id/saved` takes only an entry ID and uses the same fresh inspection, one-use token, owner, revision and origin checks as manual entry. The selected account stays bound through the next sign-in step and across broker restart. A password-only step cannot switch to a different staged username. Choosing new details clears automatic selection. A missing or rejected saved entry leads to fresh secure input, not another account. Selection and OTP submission do not create duplicate password records.

## Payment cards

Cards have an item name, cardholder, number, expiry month/year and an optional security code (CVC/CVV). The number is normalized by removing spaces and hyphens, must contain 12–19 digits and pass a Luhn check, and cannot be a repeated digit. Expiry must be the current month or later and no more than 30 years ahead. Security codes must contain three or four digits. Unknown fields are rejected.

Card secrets use AES-256-GCM in a separate `vault_cards` table with their own type/owner/record binding. Existing login records and ciphertext remain unchanged. Lists return only the card name, inferred brand, last four digits, expiry and timestamp. Details add the cardholder and a `hasSecurityCode` flag. Explicit `POST /api/vault/:id/card-number` and `/security-code` requests return only the requested secret for Show or Copy. A missing security code returns a fixed 404 response. All Vault routes are private, owner-bound and no-store. Card numbers and security codes never enter page caches, chat, agent context, Inspector or ordinary logs.

Card edits keep the saved number unchanged until Change card number is selected and a replacement is entered. Cancel change clears the replacement. Card edits lock and recheck the owner after key access. A blank or omitted replacement number or security code preserves the latest stored value. An explicit `securityCode: null` removes the saved code. Security codes share the card's encrypted payload and owner/record binding; legacy cards without one remain readable. Delete removes only the owned entry. Cards cannot be selected or filled through any website login path, and no purchase or card-autofill capability is exposed to the agent. Card storage does not verify issuer status, available funds or merchant acceptance.

## Sign-in methods

The secure form can offer observed Google, Apple, Microsoft, GitHub or Facebook sign-in buttons and observed email, SMS, authenticator or backup-code choices. `POST /api/credential-requests/:id/method` consumes the current request only after rechecking the task revision, origin and current supported control. This starts the website's flow and resumes inspection; it does not claim completed authentication or create a managed Google connection. A different origin needs a new secure request.

OTP values go to the broker and are never written to vault or request records. Users still obtain and enter their email, SMS, authenticator or backup codes. Split-digit code inputs, separate-window sign-in, device passkeys, hardware keys, iframe login and remote manual control are unsupported. A button that opens a popup only after a script runs may not be detectable in advance; the resulting flow still needs inspection. Signing in in another browser does not sign in this task browser. Push prompts and CAPTCHA can require external user action, and entering a code does not bypass additional verification.

## Browser lifetime and observation

Creating a secure request holds the browser through that form's ten-minute expiry. Other waiting-user and approval steps request a thirty-minute hold; the adapter caps each hold at thirty minutes. A hold prevents idle cleanup, not every process failure. Form expiry does not immediately close the page. The default browser idle limit is thirty minutes, and active inspector reads refresh activity. Normal cleanup closes the browser and retains its last masked screenshot.

Screenshots and bounded screen metadata are stored with mode 0600 in the private runtime directory. Metadata strips URL query strings and fragments and does not store credential values. The inspector labels a capture as live or last-known and includes its capture time. After a server restart, a nonsecret session can reattach to its existing daemon through the socket. Reading the inspector never launches a browser, opens a URL or replays credentials. A recovered session that handled credentials serves only its cached image because its redaction values existed only in memory. Further observation or entry requires an explicit reopen. Older sessions without stored screen metadata may have no recoverable image.

Passwords can become visible to page JavaScript after injection, and session cookies are credentials too. Suppressing normal tool output alone is insufficient: the agent must not have arbitrary browser JavaScript, CDP, profile-file, or trusted-process access. The adapter masks protected fields and known credential text, locks observation during entry, and redacts known values and common OAuth URL parameters. These controls cover the tested DOM forms, not every hostile page, canvas, image or script behavior. Screenshots, profiles and browser session data still need private storage and retention controls. The separate Linux workspace uses normal Docker networking without a Sidekick egress firewall. Its mounts still exclude the authenticated browser profile and private broker socket. The [saved-details report](testing/results/2026-09-25-vault-details.md) covers owner-bound reads and the rendered details, Show/Hide, Copy, retry, keyboard and narrow-layout flows with fake accounts. All 548 integration tests passed for that change.

The focused browser/vault run passed 22 tests, including staged identifier → password → OTP forms, a disabled Next button, method selection, split-code rejection, origin and revision checks, single-use requests, encrypted storage, migration preservation, waiting holds, socket reattachment and cached-screen recovery. Tests use synthetic credentials and disposable database schemas. Isolated real Chrome checks also passed staged login and screenshot recovery with synthetic content; no live X account login was tested. Live website authentication and Keychain authorization remain separate evidence. See the [validation record](verification.md) for the current full application checks.
