## Scope and access

Research tasks use public web search or read-only access to the connected Linear and Notion accounts. A task can also use a synthetic file that the user uploads as input. The file can set the search criteria or describe the user's needs. Web or connected sources must support facts about external people, companies, roles, products, and prices. Do not send an uploaded file to a public site. Public cases need no account. Linear and Notion cases need their existing grants; check them at run time. R01–R14 are one-time tasks. S01–S05 below test scheduled research as a separate group. No case needs Gmail, Hex, or a LinkedIn login. The tasks send no email or application and change no connected page or issue. A public site can still block access; record that result.

The file and channel checks below test how Otto shows completed web research. They use known synthetic files when a fixed display check is needed. They do not change the web-only source rule for research tasks.

## Run rules

1. Use a new task for each R01–R13 case. Run follow-up case R14 on the completed R01 task. Run S01–S05 in separate test conversations. Start with a fresh conversation in the test environment when possible.
2. Record the commit, model, channel, start time, end time, and reported cost. Use the actual cost record when it is available. Mark an unavailable cost as **unknown**, not zero.
3. Freeze each exact prompt, input file, source set, and check before the first run. Record the run date. Do not change a check after seeing a result. Use current public sources for web cases. Do not use a saved answer as a source.
4. Give the agent only the prompt and the stated input files. Do not add hints during the run. Record each question and each user answer.
5. Check every output row for required fields and duplicate entries. Open each source that supports a required field and check its exact claim. Review at least five rows in depth for draft quality and source fit. A working URL alone is not proof.
6. Give each check a result of **pass**, **fail**, **blocked**, **not run**, or **not applicable**. A case passes only when all its applicable checks pass. A missing account, missing input, or insufficient public source supply blocks the case; it is not an Otto failure. Record the last completed step.
7. Keep a short human review for clarity and usefulness. Do not let that review replace the required checks.

For R01, define **European** as based in an EU member state. Define **mid-size** as 50 to 500 employees in a dated public source. Accept Head of Operations, VP of Operations, or COO as the contact role. A public source must support the Shopify claim. An unknown personal email address must say `unknown`; it must never be guessed. If these criteria make ten valid rows impossible in the time limit, the case fails and the agent must state the shortfall.

## Common checks

These checks apply to each case when relevant. The case table adds task checks.

| B3  | The answer names the sources, files, and accounts that Otto used. Each important factual claim has a source link.                           |

| B10 | The web chat shows each completed file once, with a clear name, type, and open or download action. The file belongs to this owner and task. |

## Red-to-green run loop

1. Freeze this matrix, the exact prompts, input hashes, source snapshots, and the model settings. Start every case as **not run**.
2. Start each case through Otto's chat with the real model and normal task tools. For S01–S05, also wait for the normal due-time dispatch and record each result message. Record task IDs, tool and file events, visible chat or channel messages, elapsed time, and cost. Use no evaluator hints during the run.
3. Score each semicolon-separated task check in its table row as `T1`, `T2`, and so on, from left to right. Score applicable common checks B1–B10, the time target, and the relevant file checks. Mark a case **red** when any required check fails. Mark a source or account gap **blocked** before the run, not red.
4. Group red checks by cause. Reproduce one cause with the smallest focused test or recorded task trace. Change only the owning code path. Do not add a prompt rule, branch, or fixture value for one case.
5. Run the focused check, the failed end-to-end case, a related holdout, and any case that shares the changed path. Then run the repository checks required by [AGENTS.md](../../AGENTS.md). Repeat until the required checks pass.
6. Run the full R matrix, holdouts, file checks, and S extension on the same commit and model settings. Mark the one-time research group **green** only when R01–R14, V01–V06, and the required file checks pass without a blocker. Mark the scheduled research group **green** only when S01–S05 and V07–V09 pass their due-run and owner-message checks. Score an observed site closure as a sourced finding, with unavailable pages clearly named. Report channel fixture checks and live channel checks separately.
