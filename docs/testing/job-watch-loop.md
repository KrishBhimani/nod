# Job and opportunity watch evaluation

This plan applies the [agent eval loop](https://linear.app/n8n/issue/LAB-390) to [LAB-390](https://linear.app/n8n/issue/LAB-390) and its two listed variants. Use one record for each attempt. Keep the answer key, CV, account data, page copies, and full traces under `.local/evidence/lab-390/`. Do not put them in Git or Linear.

The goal is a daily report with new roles, clear fit scores, and three role-specific cover notes. A saved schedule is only setup. A case passes after the normal scheduler starts two due turns and the owner receives both results. The second result must not show a role from the first result as new.

## Shared checks

Use `blocked` for a missing input, account, source supply, or test service before scoring. A case passes only when every required check passes in one attempt. `Not applicable` and `error` do not count as passes.

## Run and repair

1. Check the test environment with a small, read-only task. A service failure is an environment error.
2. Record the tested commit, model, owner, channel, time zone, exact prompt hash, input hashes, source key version, start time, end time, and actual cost or `unknown`.
3. Give the agent only the prompt and input file. Use the normal app chat, browser, Vault, and scheduler. Do not add the answer key to the agent workspace. Do not use a real recipient or submit an application.
4. Observe two normal due turns for JW-01, JW-03, and JW-04. Check the owner message, file bytes, source pages, and actions after each turn. A saved schedule or a green judge result alone cannot pass.
5. Before a fix, record the failed check, likely cause, trace prediction, and evidence that would reject the cause. Class the result as an agent gap, source change, setup fault, or evaluator fault. Keep the red attempt.
6. Fix a general cause in its owning module. Run a focused check, the same case, one held-out case, and related schedule, browser, file, or approval regressions. Then run `npm run check`, `npm run test:integration`, and `npm run build`.
7. Keep a case red until its base run, held-out run, and related regressions pass on the same commit and model. Choose any repeat count before repeat runs. Report both the share that passes once and the share that passes every time.

Use [LAB-377](https://linear.app/n8n/issue/LAB-377) and [LAB-381](https://linear.app/n8n/issue/LAB-381) as schedule and change-detection regressions when a fix touches those paths. Record fixture, normal app, UI, and live account evidence in separate fields. A fixture pass does not show that a live account case passed.
