Two earlier full-suite runs exposed obsolete fixtures and a real duplicate state-file write during local runtime shutdown. Those were repaired before the passing full run. Tests use dedicated disposable databases and do not rotate the existing local application's database credentials.

The latest Cloudflare fix forces `SIDEKICK_BIND_HOST=0.0.0.0` for both private process roles. Gateway/tenant HTTP forwarding uses the platform TCP-port Fetcher inside fixed-error handling, preserving SDK lifecycle monitoring while avoiding raw SDK proxy errors and implicit tenant restart. The 20-test package result, both dry runs and the passing 1,023-test root rerun include the settled changes.

The root rerun also reproduced and repaired a fixture cleanup race: `pool.end()` could resolve before PostgreSQL closed the backend socket, so an immediate disposable-database drop still saw an active connection. Cleanup now waits within a bound and does not use forced database deletion. This was a test-resource cleanup failure, not a production tenant-isolation failure.

The subsequent review and container checks added 32 passing regressions and corrected storage validation/error normalization, browser launch state, unused E2B disposal, static image structure checks, onboarding loading/retry and stale-sign-in feedback. The deployment workflow also rechecks the main SHA immediately before publication; isolated execution of that exact shell gate passed current, superseded, invalid-SHA and lookup-failure cases. Superseded builds skip publication and lookup failures stop it. Delayed registry requests are covered by real PostgreSQL regressions: an old claim cannot recreate released ownership and an old release cannot remove a newer claim. Tenant revisions and registry release tombstones persist across cleanup and restart. CI run [`36259381856`](https://github.com/n8n-io/sidekick/actions/runs/36259381856) passed for implementation commit `1303d732`, including the full root suite, client build, Cloudflare checks and bundles, production image, container filesystem/user validation and secret scanning.

## Actual local Cloudflare process checks

A separate local Wrangler run built the production amd64 Node image and served the real Worker-to-gateway container path on loopback port 4349. Gateway health returned `ok: true` and the synthetic `local` release. Anonymous session state had no user or developer capability; account state and avatar requests returned 401. Runtime startup, storage-broker and internal channel-claim paths returned 404 through public ingress, and a foreign-origin login returned 403.

The run used its own synthetic PostgreSQL database and no real provider credentials. Its databases, labeled image and SDK proxy container were removed, and port 4349 was confirmed closed. Shared PostgreSQL and unrelated containers were preserved. This first run established local Worker/gateway wiring and denial behavior. A subsequent two-user run exposed an upload failure: signature verification consumed the raw multipart stream before the installed file parser could read it. The tenant now parses already-authenticated bytes with the same file/field limits and validates the complete form before storage or transcription. Real HTTP regressions cover successful upload/transcription, tampering, replay, malformed tails and size/count limits.

The fresh-source follow-on then passed through the real Worker, gateway and two tenant containers with signed Better Auth synthetic sessions. File upload returned 200 through the private tenant-to-local-R2 broker; the owner retrieved exact bytes with 200 and a correct partial response with 206. A foreign user received 404 for that artifact, and a mismatched account fence received 401. Anonymous and private-route denial checks also passed. The isolated database, two tenant roles, containers, SDK proxies and experiment image tags were removed afterward. This proves local container/storage wiring and synthetic ownership boundaries; it does not establish Google login, production R2, E2B, Pi restart recovery in that stack or a deployed Cloudflare service.

## Actual local Pi restart check

A separate 9.462-second experiment used the stock hosted tenant process, signed runtime-host HTTP and exactly two development model requests. The first synthetic chat completed and stored its private Pi checkpoint in PostgreSQL. The process then stopped, released its lease and had its entire temporary session directory removed. A fresh process acquired generation 2 and resumed the same task. Its outbound model context contained the restored prior conversation and resume instruction, and its final answer recalled the synthetic marker. The checkpoint version advanced without tool intents.

The experiment used the configured development model and no production credentials, Google login, Composio, E2B or Cloudflare deployment. The temporary database, restricted role and tenant processes were removed; the shared test PostgreSQL service was preserved. This proves PostgreSQL-backed conversation recovery across an actual local tenant restart. It does not establish R2-backed checkpoint recovery or recovery during an active external action.
