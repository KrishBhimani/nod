# C22 conversation-routing probe, 2026-09-25

The isolated acceptance run reproduced a routing error with a real OpenAI model and synthetic Northstar data. A browser task waiting for credentials accepted a queued invoice follow-up. A second request for a screenshot of that same signed-in page became a new outcome and browser task.

Read-only PostgreSQL inspection showed that the first follow-up committed at `00:53:10.729Z`. The next router operation began about `00:53:10.879Z` and returned successfully after 791 ms. The candidate query includes accepted pending messages and orders the updated original outcome first. A reconstructed candidate payload included the queued invoice request. This was a classification failure, not a timeout fallback or evidence of a missing pending-message write. The recorded timestamps reconstruct request timing; the complete original routing request was not retained.

Using the unchanged routing instructions and reconstructed synthetic candidate payload:

| Model        | Observed decisions                                                                                | Duration      | SDK-estimated cost per call |
| ------------ | ------------------------------------------------------------------------------------------------- | ------------- | --------------------------- |
| GPT-4.1 nano | Both screenshot follow-ups incorrectly started new work; two independent requests stayed separate | 0.742–0.956 s | Not recorded in this probe  |
| GPT-4.1 mini | 6/6 expected: four continuations and two independent requests                                     | 0.835–1.590 s | USD 0.000507–0.000516       |
| GPT-5.4 mini | 6/6 expected on the same six messages                                                             | 0.712–2.267 s | USD 0.001022–0.001036       |

The six messages covered the exact failed screenshot request, a screenshot paraphrase, an independent browser/design request, a new reminder about the same invoices, a follow-up to the existing reminder, and paid-invoice details after sign-in. Adding explicit pending-request data to nano did not reliably fix the association and changed one independent reminder incorrectly. An association-only nano experiment also failed to select the browser outcome. Those experiments were not adopted.

The default is now GPT-4.1 mini. Explicit `ROUTING_MODEL` configuration is preserved. Provider and server use one five-second budget, with zero retries and the existing safe fallback. The modest increase allows more room than the earlier three-second limit, which had timed out once in a separate mini probe. There is no second model call or keyword-routing override. Credential, approval, owner, channel and revision checks remain unchanged.

Focused fixtures cover the selected default, explicit model override and usage labels, cancellation, strict decision validation, foreign IDs, and a second route seeing already-pending follow-ups without consuming them. This probe does not establish general semantic accuracy, production latency, a provider bill, or successful account access. It made only bounded classifier calls with synthetic data; the harness and live owner state were not changed.

## C18 preference correction, 2026-09-25

Run4 correctly kept both Northstar follow-ups together, but queued a correction to a travel preference behind that unrelated browser task. Read-only reconstruction found that the earlier preference and its assistant reply belonged to an execution with no outcome. Candidate-only routing excluded both messages. The current mini classifier reproduced the wrong continuation in 954 ms. Adding the missing ordinary conversation and its null outcome provenance produced conversation in an initial 630 ms probe. The full original classifier request was not retained.

The server now supplies up to 12 additional same-owner, exact-channel, current-generation messages, each bounded to 1000 characters. Messages already supplied in candidate transcripts are excluded. Only role, text and nullable outcome ID cross this port; no task IDs, secure-entry records or values are added. Provider instructions distinguish general preference corrections from changes to a specific deliverable. Model selection, the five-second budget and wait/approval enforcement remain unchanged.

A final real GPT-4.1 mini probe on reconstructed synthetic data produced the expected result for the exact preference correction, its paraphrase, both Northstar follow-ups, a separate reminder, a distinct-site browser request and an explicitly separate same-site browser request. These seven calls took 0.845–1.078 s. The first five reported SDK estimates of USD 0.0004764–0.0005276 per call; costs were not captured for the last two controls.

One additional ambiguous control, “Open https://example.com and tell me its heading,” continued the active browser outcome. The reconstructed candidate also used example.com as its login destination. That residual same-site ambiguity was recorded without adding a phrase-specific override. This probe is evidence for the observed regression, not a general accuracy guarantee or a live account test.

The combined routing/provider/acknowledgement fixtures passed 25/25, with TypeScript and architecture checks. New fixtures verify ordinary context, transcript deduplication, input caps, and channel/reset exclusion. The acknowledgement fixture now controls its timer and proves the write is waiting on a PostgreSQL row lock before changing the revision, avoiding a load-dependent test race.
