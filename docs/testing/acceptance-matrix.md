# Computer-use acceptance matrix

This is a product-derived test plan. No Slack connector or connector-discovery tool was available in the session, so none of the examples below are attributed to Slack. A case passes only after its visible workflow and its stated checks have been observed. Unit fixtures, planned cases and live provider checks are separate evidence.

## Isolated environment

From the repository root, after the normal Docker workspace and PostgreSQL are available:

```sh
npm run build
npx tsx scripts/e2e-otto.ts
```

The app is at `http://localhost:4320`. Open `http://localhost:4320/e2e` for operator instructions and synthetic credentials. The manifest printed at startup identifies the temporary directory, disposable PostgreSQL and pg-boss schemas, workspace container and timing file. `http://localhost:4320/e2e/status` exposes timing metadata for this isolated run. Do not submit work to the normal app at port 4310 during these tests.

The harness uses the configured real Pi model and API key, the real semantic conversation router, real Chromium through agent-browser, the real Vault broker, app workers and a separate Linux workspace container. Model and routing calls incur normal provider usage. A router timeout or unavailable routing model falls back to ordinary conversation; record that result rather than claiming outcome continuity. Google consent/data and the Northstar website are synthetic. Speech and messaging transports are disabled. No real Google account, email recipient or chat-provider delivery is exercised. Existing production connections, credentials, conversations and workspaces are not copied.

Only the task browser maps `https://example.com/__otto_e2e__/...` to the synthetic site. A temporary certificate for that exact host is trusted through a certificate-specific browser launch argument. Other destinations pass through the existing public-network guard. Paths outside the fixture prefix on example.com are unavailable in this harness. The user's browser receives no certificate exception; it opens only the local app and operator page.

The fake integration redirects its own consent URL to a local fixture page. The real connection callback state checks, account rows, account selection, read policy and approval execution still run. This validates the app workflow, not Google's external OAuth service, grants, token refresh, Composio availability or webhook delivery.

Stop with Ctrl-C. The harness closes workers/browsers, removes its workspace container and drops only its generated schemas. The temporary directory remains for evidence and contains private browser/session files and an ephemeral certificate key. Keep it local and remove it when the evidence is no longer needed. The Vault master key lives only in this harness process; restarting this script creates a fresh environment. Process restart recovery is a separate fixture check, not a claim of this harness.

## Timing and evidence

`timings.jsonl` records UTC timestamps without prompts, replies, form values or provider keys:

- `chat_request_received` and `chat_request_accepted` pair a request ID with its task ID.
- `first_visible_delta` and `assistant_message_saved` identify visible response timing; saved messages include the database timestamp. Historical acknowledgement events do not require or authorize a canned progress message in current runs.
- `task_state` records revision/status transitions, including waits, resume, completion, failure and cancellation. Sampling is every 250 ms; a very short intermediate state can be missed.
- `fixture_password_submit` / `fixture_otp_submit` record accepted/rejected booleans only; `fixture_portal_view` proves the browser reached the authenticated fixture.
- `fixture_account_connected`, `fixture_integration_execute` and `fixture_integration_write` record synthetic account/action IDs without arguments or message bodies.
- `scheduled_job_started` includes queue timing and, when registered, expected due time and lateness. App task creation and first response are separate timings.

Before C16 or each C24 occurrence is due, obtain its schedule ID from the app response or `/api/schedules`. For C16, confirm `kind: once`, the saved `runAt`, `timeZone`, `nextRun` and enabled state. For C24, confirm `kind: recurring`, its cron, `timeZone` and next absolute occurrence. Register the next C24 occurrence after the prior one completes, before it is due. Register the intended absolute occurrence:

```sh
curl -fsS http://localhost:4320/e2e/expected-run \
  -H 'Content-Type: application/json' \
  -d '{"scheduleId":"<isolated schedule UUID>","dueAt":"<expected UTC ISO timestamp>"}'
```

Use the intended minute from the user's schedule, not the job's observed enqueue time. The harness observes the real `scheduled-task` delayed job; the persisted `schedule_runs` entry links its scheduled occurrence to the internal task. Compare the Schedule history timestamp/status with the queue timing and the first useful reply. A succeeded execution status alone does not prove the requested outcome happened. Report `scheduled_job_started.startedAt − dueAt` and first useful reply minus `dueAt`. A suggested local acceptance target is no early execution and worker start within 65 seconds of the due minute; report actual latency even if it exceeds that target. This target is a test criterion, not a guaranteed scheduler SLA.

For each case, save: case ID, UTC start/end, outcome ID when present, task ID/revision, source message ID when relevant, UI screenshot paths, expected/actual result, relevant timing entries, exact failure, and the evidence class. Use **real app + model + browser with synthetic data**, **deterministic fixture**, or **live provider**. Do not attach credential forms containing values or copy full private sessions into a public report. Empty evidence is **not run**, never a pass.

## Harness verification

```sh
npx tsx --test tests/e2e-harness.test.ts
```

These checks validate password/OTP sequencing, audit redaction, the fixed TLS mapping/public-guard delegation, synthetic consent state and account-scoped execution. They do not run an LLM, Chromium or the visible acceptance cases.
