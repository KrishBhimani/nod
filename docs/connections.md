# App connections

Otto shows connected accounts and available services in **Apps**. A user can select **Connect** or **Add account** there. In chat, `manage_apps` can show accounts and start the same connection flow. When a chat task starts a connection, Otto puts one sign-in link in the conversation. The callback returns to chat and queues that task again if its owner, conversation, and revision still match. A repeated callback can reuse the verified token exchange if account inspection failed before the app saved its account row. The provider can still require a sign-in or consent click. A prior grant can make that step shorter.

The direct Notion and Linear packages use [Agent Plugins v1](https://agent-plugins.org/specification) `plugin.json` and `mcp.json` files under `plugins/`. Each package declares one fixed Streamable HTTP MCP endpoint. The direct provider loads and checks those files. Otto manages OAuth discovery, dynamic client registration, PKCE, callback checks, encrypted tokens, refresh, account state, and tool calls. The package files contain no credentials. This implementation loads the two bundled MCP packages. It does not load arbitrary packages or CLI servers.

Notion uses its [hosted MCP server](https://developers.notion.com/guides/mcp/overview). Linear uses its [read-only MCP endpoint](https://linear.app/docs/mcp) and the `read` OAuth scope. Otto permits Notion search and page reads, and Linear project, issue, team, and status update reads. The direct adapter has no write or watch action. It checks the live MCP tool list when an account is connected. Composio remains the provider for Google and Slack services and their supported events. Existing Composio Notion accounts keep their provider ID and continue to work; new Notion and Linear accounts use the direct provider. When both Notion providers have an active account, Otto lists the direct account first and selects it for an action without a stated account. The live tool catalog favors the direct tool schema. A stated account ID still selects its saved provider. Tokens and account IDs do not move between providers.

`src/server/integrations.ts` owns the catalog, account selection, consent attempts, callback state, and read policy. It accepts extra provider adapters and routes each saved account by provider ID. `src/providers/direct/oauth.ts` owns direct OAuth state and encrypted tokens. `src/providers/direct/mcp.ts` owns MCP transport. `src/providers/direct/integrations.ts` maps approved actions to live tools. `src/server/composition.ts` selects the adapters. Local mode uses a Keychain key on macOS or a configured environment key. Hosted tenant mode uses its derived private key and tenant SQL namespace. Direct OAuth tokens and pending PKCE data are encrypted with AES-256-GCM in `direct_oauth_accounts`. Tokens stay out of the browser client, model, logs, and workspace. Disconnect deletes the saved token; a user can also revoke the grant at the provider.

Disposable database fixtures cover callback state, encrypted token storage, provider routing, account selection, and chat callback handoff. They use substitute provider responses and do not prove a real grant or MCP read. Public OAuth metadata discovery and dynamic client registration returned valid responses from Notion and Linear on 2026-09-28. Live account consent, MCP reads, token refresh, and hosted consent still need checks with authorized accounts. [Codex plugin authentication guidance](https://developers.openai.com/plugins/build/auth) supports client-managed OAuth with issuer checks and PKCE; Otto applies those checks at its own trusted server boundary.
