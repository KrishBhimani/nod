# Cloudflare deployment adapter

The public Worker serves built web assets and sends `/api/*` to one private Node gateway. The gateway authenticates Google sessions, provisions a tenant SQL role and private schemas, and sends signed requests to that user's Node container. With `COMPUTER_PROVIDER=cloudflare`, each owner also gets separate browser and workspace containers through a private command broker. Application code stays in the Node runtime image; computer images contain no service keys.

The pilot admits eight users and keeps the gateway and admitted tenant runtimes available for background work. A minute Cron wakes the gateway after an interruption; gateway recovery rehydrates registered owners, and signed lease heartbeats govern continued work. Computer containers can checkpoint and stop after idle time. Increasing admission requires matching all role limits and reviewing database connections and cost; the provisioner has a hard ceiling of 400 roles.

| Class                        | Image tag                                | Instance type | Maximum per environment |
| ---------------------------- | ---------------------------------------- | ------------- | ----------------------- |
| `GatewayContainer`           | `sidekick-<environment>:<SHA>`           | `basic`       | 1                       |
| `TenantContainer`            | Same runtime image                       | `basic`       | 8                       |
| `BrowserComputerContainer`   | `sidekick-<environment>-browser:<SHA>`   | `standard-1`  | 8                       |
| `WorkspaceComputerContainer` | `sidekick-<environment>-workspace:<SHA>` | `basic`       | 8                       |

## Local checks

Use the repository's supported Node version and an available Docker engine.

```sh
npm ci
npm run build
npm --prefix deployment/cloudflare ci
npm --prefix deployment/cloudflare run check
npm --prefix deployment/cloudflare test
cd deployment/cloudflare
npx wrangler deploy --env development --dry-run --containers-rollout=none
npx wrangler deploy --env production --dry-run --containers-rollout=none
```

Package tests use synthetic identities, lifecycle substitutes and in-memory object storage. Dry runs validate bundling and configuration without starting containers or deploying. Separate actual local checks have exercised native Container.exec, R2 emulation, Linux amd64 images, browser actions, cancellation/drain and restoration after VM destruction. These ran under Docker Desktop on an ARM64 host with synthetic lease authority. They do not establish deployed Cloudflare, live R2 or account acceptance. Track exact evidence in the [acceptance record](../../docs/testing/results/2026-09-26-cloud-hosting.md).

For the actual local stack, set `COMPUTER_PROVIDER=cloudflare` in the private hosted development file and run `node scripts/start-hosted.mjs --check`, then `node scripts/start-hosted.mjs` from the repository root. The launcher selects `scripts/start-cloudflare-local.mjs`, generates owner-only local configuration, starts Wrangler on `http://localhost:4330` and uses R2 emulation. It never deploys or supplies cloud deployment credentials to containers. Use a Docker-reachable development database and the development Google callback at `/api/auth/callback/google`. Rebuild `dist/web` after UI edits. [Complete local setup](../../docs/development.md#hosted-mode-on-your-computer).

On macOS and Linux, local Ctrl-C/SIGTERM first uses the existing signed prepare protocol while Wrangler remains alive. It waits for natural task completion, non-forced computer checkpoints and confirmed exact-generation stops, then exits with the barrier still closed. The next launcher verifies its private journal and stable local installation identity before aborting that same prepared operation. This 40-hex identity is supplied to Gateway/Tenant image builds and gateway configuration; it is not a deployed commit claim and does not change production SHA validation. Failed drains retain the stack and fences. `node scripts/start-hosted.mjs --env <file> --resume` explicitly resumes the recorded operation without launching Wrangler. Keep the journal and lock files; after an external kill, verify the exact owner process has ended before reconciling a stale lock. Stop cleanly before watched source edits, since hot rebuilds bypass this handshake. [Shutdown, recovery and limitations](../../docs/development.md#hosted-mode-on-your-computer).

## Environments and secrets

`wrangler.jsonc` has separate `development` and `production` Workers, four Durable Object classes, EU R2 buckets and container applications. The production Worker is named `sidekick`; the repository targets `https://sidekick-development.n8n-maintenance.workers.dev` and `https://sidekick.n8n-maintenance.workers.dev`. Production was manually deployed on 2026-09-27 and passed release health, anonymous authorization checks and Google login. First-user onboarding exposed a deployment completion bug; full production acceptance remains in progress. The cloud development destination has not been deployed. Provider projects, buckets and image tags keep their existing development/production names. The additional computer provider uses Jan's existing Cloudflare plan and avoids requiring an E2B paid account. No plan change was made; normal Cloudflare compute, storage and request usage still applies. E2B remains an optional provider.

For self-hosting in another account, change the Worker/resource names as needed and replace each `SIDEKICK_PUBLIC_URL` with that deployment's canonical HTTPS origin. Keep the corresponding `GATEWAY_ENV`, Google OAuth callbacks, integration callbacks and GitHub environment variable consistent with it. Set the selected Cloudflare account through the deployment environment, rather than committing account credentials. Create both private R2 buckets in the configured EU jurisdiction.

Store one `GATEWAY_ENV` Worker secret per environment. Its value is the JSON object of server environment variables used by the Node gateway: the control-plane database URL, auth settings, tenant key material and operator-selected provider configuration. The Worker overrides process mode, canonical origin, environment, data directory and port. Never use build arguments, Vite variables or checked-in Wrangler `vars` for secrets.

Keep the compact JSON under 5 KiB including the injected `SIDEKICK_RELEASE`: this is Cloudflare's per-variable limit. Include only the provider keys actually used, rather than copying an entire shell environment. The deployment script rejects an oversized secret before publishing. [Worker limits](https://developers.cloudflare.com/workers/platform/limits/#environment-variables).

Before sharing signup, customize the [privacy notice template](../../docs/privacy-notice-template.md) into `public/privacy-notice.md`. That source file and its raw Markdown are intentionally public; include only reviewed notice text with the actual operator/contact, providers and retention process. `npm run build` copies it to `dist/web/privacy-notice.md` in the image. Set `SIDEKICK_PRIVACY_NOTICE_FILE=dist/web/privacy-notice.md` inside `GATEWAY_ENV`; keep the notice text out of the 5 KiB JSON budget. The gateway reads the UTF-8 file at startup, bounded to 128 KiB and 32,000 characters, and serves anonymous `/api/privacy`. A configured invalid or unreadable file fails startup; omitting the setting permits deployment without a notice. Rebuild and restart for notice changes. Verify the displayed `/privacy` page while signed out on the deployed origin and set its HTTPS URL in Google OAuth before inviting users. The release smoke test does not establish this manual readiness check or Google's branding status. [Google login and rollout requirements](../../docs/production.md#privacy-and-google-sign-in).

The gateway builds each tenant's environment explicitly. Required fields are `SIDEKICK_OWNER_ID`, `SIDEKICK_ENVIRONMENT`, `SIDEKICK_MODE=tenant`, `SIDEKICK_RUNTIME_GENERATION`, `SIDEKICK_RUNTIME_SECRET`, `SIDEKICK_RUNTIME_LEASE_EXPIRES`, `DATABASE_URL` and `PGBOSS_SCHEMA`. The Worker checks that the SQL role and jobs namespace match the opaque hash of the supplied owner/environment. Only derived tenant credentials and the configured runtime provider keys belong in that environment. The control database credentials, Google login secret, tenant derivation master key and privacy-notice configuration stay in the gateway.

Both Node process roles run `node --import tsx src/server/index.ts`; bootstrap forces `SIDEKICK_BIND_HOST=0.0.0.0` and port 4310 inside the private container. They use `/data` as an ephemeral working directory. The two computer images run a fixed entrypoint under `tini` as the unprivileged `node` user, expose only internal `/health` on port 4311 and receive an empty service environment. The browser waits for an actual private control-socket connection before reporting readiness. The workspace has Python/Node CLI tooling and no browser or application server source. Docker allowlists include build configuration and public assets, while excluding `.env`, `.local`, browser profiles and database files; the root allowlist also covers Wrangler's copied-Dockerfile build context.

## Private transport

Only the fixed gateway Durable Object may call `http://sidekick.runtime`. The handler verifies the platform-supplied class and container ID. These operations have no public Worker route:

| Request                            | Input                                                | Result                                                                        |
| ---------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------- |
| `POST /runtime/start`              | `{ownerId, env}`                                     | `{ok:true, generation}` after startup                                         |
| `POST /runtime/status`             | `{ownerId}`                                          | `{generation, stopped, status}`                                               |
| `POST /runtime/stop`               | `{ownerId, generation}`                              | `{ok:true, generation, stopped:true}` only after confirmed termination        |
| `POST /runtime/deployment-status`  | `{}`                                                 | `{closed}` from the persistent gateway admission barrier                      |
| `POST /runtime/prepare-deployment` | `{ownerId,generation,nonce,targetRelease,deadline}`  | Exact-generation clean checkpoints and confirmed stop, or busy/unsafe refusal |
| `POST /runtime/deployment-stopped` | `{ownerId,generation}` with nullable generation      | Read-only `{stopped,generation}` proof for journal-loss recovery              |
| Any method `/<ownerId>/api/...`    | Original body and signed `x-sidekick-runtime` header | Tenant HTTP response, including streaming bodies                              |

The handler removes the owner prefix before the actor verifies the signed request target. Startup stores only owner/environment/generation, a configuration digest and stopped state in the Durable Object. It does not persist the bootstrap environment or credentials. A changed generation requires an explicit stop of the exact prior generation and a larger generation number. Stale cleanup cannot stop a replacement. A stopped actor is not automatically started by forwarding an ordinary request. HTTP forwarding uses the platform TCP-port Fetcher inside fixed-error handlers; SDK helpers continue to manage lifecycle/startup monitoring, but the proxy does not return or log their raw HTTP errors.

Tenant replacement revokes computer access and must confirm that the tenant and both computer roles stopped. A stop acknowledgement for only the Node actor is insufficient. Stopping a never-used computer role confirms physical destruction, rechecks authority and records that exact owner/environment/role/generation as ready and stopped before permitting a newer generation. Failed destruction or lost authority cannot publish that marker. Delayed storage and computer requests include the immutable runtime generation and cannot adopt a replacement grant merely because the platform reuses a container identity.

Deployment drain records its exact attempt before forwarding the signed Node pause request and stores successful acknowledgement separately. The computer drain requires that successful receipt plus a witness of the same live process, or independent physical-stop confirmation. Resume removes computer authority before reopening Node admission and retains its identity for retries after lost responses; a delayed drain acknowledgement cannot restore that authority. A known busy prepare retains HTTP 409; unknown failures return a fixed 503. Neither response reopens admission. No deployment drain force-cancels work or forces a held browser to close.

Recovery inspection performs no startup, lease adoption, checkpoint, stop or fence clearing. It requires the persistent gateway barrier to remain closed, the exact tenant generation to be physically stopped, and both roles to be either unused or recorded clean and stopped. Dirty, restoring, uncertain, active, newer-generation or still-starting state refuses a clean receipt. Idle checkpointing alone leaves the persisted stopped marker unset and does not establish this stricter recovery proof. [Local startup and Wrangler constraints](../../docs/development.md#hosted-mode-on-your-computer).

The SDK's SIGTERM acknowledgement does not establish tenant termination. A tenant stop waits up to ten seconds, including the signal request, for both native termination and a terminal SDK state. Timeout leaves revocation in place without a stopped receipt, lease release or forced kill; a later exact-generation retry can confirm the completed shutdown.

Only tenant containers may call `http://sidekick.control`, and only `POST /api/internal/channels/claim` or `/release`. The handler checks the platform identity, forwards the signed runtime header and body, and fixes the owner and canonical Host. The gateway independently verifies the owner's signature, request body and current SQL lease. Tenant containers cannot call runtime lifecycle operations.

Channel claim requests include a durable account revision. The registry retains released revisions to reject delayed mutations after cleanup or re-enabling. An upgrade from the earlier unversioned protocol must drain and confirm termination of old gateway/tenant processes before activating this version. Existing claims migrate at revision zero; keep tenant counters and control tombstones together during recovery.

When bootstrap or a same-release rollout prepares the already-running gateway, completion resumes its exact signed Node deployment operation before reopening the durable admission barrier. Failed resume leaves the barrier closed; completion retries use the same operation. A different-release rollout uses the newly started gateway process.

## Private files

`http://sidekick.storage/v1/objects/<encoded-key>` is a tenant-only outbound binding to the private `TENANT_FILES` R2 bucket. The trusted calling container determines the environment/owner prefix, and each request must match its current grant through `x-sidekick-generation`. Caller-supplied owner headers do not select storage. There is no listing operation, public route, or R2 credential in the Node process.

Accepted keys are `artifacts/<uuid>` and `sessions/<task-uuid>.jsonl`. GET returns bytes plus `ETag`, or 404. PUT is bounded to 16 MiB and requires `If-None-Match: *` for a new object or the previous quoted `If-Match` ETag; a stale writer receives 412. Successful writes return 204 and the new ETag. Unconditional DELETE removes only that owned key. Conditional DELETE returns 501 without deleting because R2 has no atomic conditional delete API; cleanup must retain the orphan for reconciliation rather than silently ignore a precondition. Objects always use private no-store response metadata. Durable session writers must retain and compare the returned ETag.

## Private computers and recovery

Only a tenant with a current runtime grant may call `http://sidekick.computer`. Every request includes `x-sidekick-generation` and `x-sidekick-computer-role`; the Worker binds the platform caller to one owner, environment and role. There is no public command route or computer-provider selector in the product. The trusted Worker launches fixed bridge/supervisor programs through Container.exec, while operation data travels on stdin with bounded output. Model, integration, database, login, storage and deployment keys stay outside both computers. Authorized website credentials may enter only the trusted browser path; the shell has no browser profile mount or control socket.

The browser uses `/data/<owner-namespace>`; the workspace uses `/home/node/state`, with fixed `/workspace` and `/home/node/.local` symlinks for task files and installed tools. Distinct owner/role archives live privately in R2. The checkpoint helper preserves modes, executable bits and safe internal relative symlinks, verifies per-file and archive SHA-256, and restores atomically into an absent or empty root. Limits are 256 MiB for the archive, 64 MiB for one file and 20,000 entries including the root. Exceeding a limit fails the operation; it does not silently drop files.

Workspace completion waits for the supervised process group to drain and the file checkpoint to finish before returning its terminal acknowledgement. The Python execution budget stays at 120 seconds; bounded transport grace accommodates startup, restoration and checkpointing. A platform kill acknowledgement alone does not prove descendants have stopped. Browser idle shutdown first asks the worker to quiesce; active holds or native sign-in can decline that request. A normal stop may close browser sessions before checkpointing. Checkpoints restore profile and filesystem data, not a live DOM, process memory or an unfinished action.

Computer activity, ownership and checkpoint state are recorded before side effects. Missing terminal acknowledgements, failed cleanup, dirty recovery or unknown checkpoint outcomes quarantine the role instead of replaying a command or restoring an older snapshot automatically. Keep the prior checkpoint and reconcile the uncertain state before recovery. Never clear a fence merely to make a new generation start.

## Rollout and verification

`.github/workflows/ci.yml` runs root checks, PostgreSQL fixtures, the web build, this package's checks/tests, both Wrangler dry runs and all three amd64 image builds. It checks unprivileged users, computer key/filesystem boundaries, fixed helpers, readiness and graceful shutdown. `.github/workflows/deploy.yml` starts only after successful CI on this repository's current `main` commit. It checks out that exact SHA, rebuilds it without production secrets, and serializes production deployment through the GitHub `production` environment. It does not consume build artifacts from pull-request jobs.

Configure the following GitHub environment values:

| Kind     | Name                    | Value                                                       |
| -------- | ----------------------- | ----------------------------------------------------------- |
| Secret   | `CLOUDFLARE_API_TOKEN`  | Scoped deployment token for the selected account            |
| Secret   | `CLOUDFLARE_ACCOUNT_ID` | The selected account's 32-character ID                      |
| Secret   | `GATEWAY_ENV`           | Compact JSON of the production gateway's server environment |
| Variable | `SIDEKICK_PUBLIC_URL`   | Canonical HTTPS application origin                          |

The initial account-scoped provisioning token needs Workers Admin (or legacy Workers Scripts Edit), Containers Edit, and Workers R2 Storage Edit for bucket creation. No zone, DNS, or Workers Routes permission is needed for workers.dev. After bootstrap, Workers Editor scoped to the existing Worker plus Containers Edit is sufficient for the deployment operations; direct R2 provisioning uses a separate operator token. Supplying the account ID avoids account discovery. The actual account policy must be tested before declaring CI operational. [Workers roles](https://developers.cloudflare.com/workers/authorization/workers/), [permission catalog](https://developers.cloudflare.com/fundamentals/api/reference/permissions/), [R2 permissions](https://developers.cloudflare.com/r2/api/tokens/).

After approval and rebuilding, the final CI step rechecks that the validated release is still the current `main` SHA. A superseded revision skips publishing, and a failed lookup stops the job. It then runs `scripts/deploy.mjs production` with the production credentials available only to that publication step. The script validates the origin, environment, release, hosted computer/storage configuration and required container classes. Gateway and tenant share the runtime image; the Cloudflare browser and workspace use two additional images. All selected images are pushed and resolved to immutable registry digests before application admission changes.

An existing deployment follows these steps:

1. A purpose-specific HMAC derived from `SIDEKICK_MASTER_KEY` authorizes the bounded `POST /api/deployment` control request. It binds environment, body, target and a short-lived replay-protected request ID; Google sessions and tenant credentials cannot authorize deployment. No additional long-lived key is needed.
2. The fixed gateway Durable Object persists a closed admission barrier with an immutable nonce, previous/target release and deadline. Normal API traffic and scheduled tenant wakeups stop. Health and the exact anonymous session/state checks remain available for release verification.
3. The gateway pauses each existing tenant's ingress and queue consumers while already accepted work finishes naturally. Lease renewal continues. A tenant acknowledgement is followed by clean browser/workspace checkpoints and confirmed termination of both roles and that exact tenant generation. Active browser holds or native sessions, uncertain state, missing acknowledgements or an expired safety deadline prevent activation. Deployment never force-cancels a task or clears a computer fence.
4. Only a fully prepared barrier can enter activation. `wrangler deploy --secrets-file` publishes Worker code, the pinned image references and `GATEWAY_ENV` in the same version operation. There is no earlier `secret put` deployment.
5. The script checks every selected container application for its exact current image digest and absence of an active rollout. Any present target must also contain that matching image; incomplete or malformed metadata cannot count as a finished rollout. Admission stays closed until every application verifies and the public release smoke checks pass. The barrier reopens only after a signed completion for that same nonce and target release.

For the first deployment, the script requires Cloudflare's explicit missing-Worker response, no matching container applications and an empty SQL tenant registry. API denial or unknown responses never count as absence. A managed first startup keeps admission closed until images and public smoke pass and an empty drain/completion is recorded. This bootstrap path cannot adopt an existing occupied deployment. Ordinary local Wrangler development remains open when no barrier exists.

Temporary configuration, secrets and Wrangler logs have private permissions and are removed in `finally`. Subprocess output is suppressed because failures can contain provider configuration; phase logs contain no credentials or user data. [Code and secrets together](https://developers.cloudflare.com/workers/configuration/secrets/#upload-secrets-alongside-code), [prebuilt images](https://developers.cloudflare.com/containers/guides/image-management/).

For an authorized manual development deployment, first run the same checks and build all three tags from the table with `--platform linux/amd64` and the corresponding `Dockerfile`, `Dockerfile.browser` and `Dockerfile.workspace`. Pass `--build-arg SIDEKICK_RELEASE=<SHA>` to the runtime build. Supply the values above plus `SIDEKICK_RELEASE=<SHA>` through a private environment file or secret manager, then run `npm --prefix deployment/cloudflare run deploy:development`. The public origin and gateway JSON must identify development and use development database/provider projects. The script expects every selected verified image to exist locally; it never builds with production credentials in scope.

An authorized manual production deployment uses the same image checks and `deploy.mjs production` flow with production configuration and the scoped production deployment credential. The current pilot authorizes a one-off manual validation with that credential before its ongoing use in production CI. The current pilot sequence requires successful manual production deployment and browser testing before merging; the authorized administrator merge override is conditional on that result. The production origin, Google callback, signed Composio webhook and GitHub gateway configuration are aligned, but no deployment has run. The reviewed privacy notice remains required before public sharing.

For the first cloud development deployment, use a separate empty database in the development database project and a separate private configuration with fresh application/authentication keys, the cloud origin and private storage broker. Keep the populated local database and its matching R2 emulator state intact; they cannot be adopted by this first-deployment bootstrap. This creates a fresh cloud installation, not a migration of existing local accounts or files.

Worker activation and container rollout are not atomic. Cloudflare starts the Worker/DO code update before independently replacing container instances, and a successful deploy command means rollout started. The 60-second active rollout grace is based on connection age; it is not a cleanup interval. The admission barrier therefore remains closed throughout this transition. Keep private protocols, checkpoint formats and schema changes compatible with both images. A full development deployment is required to verify the platform behavior; `wrangler versions upload` alone does not publish a container image. [Container rollouts](https://developers.cloudflare.com/containers/configuration/rollouts/) (checked 2026-09-27).

Smoke waits for `/api/health` to report the exact new image commit, then verifies that an anonymous session has no user/settings/developer access, ordinary state returns 401, private control/bootstrap routes return 404, and a foreign-origin login POST returns 403. It never signs in or contacts a user's integrations. These checks and deployment fixtures do not establish live Google, storage or webhook acceptance.

A pre-activation failure attempts the same deployment's explicit abort. Abort resumes only acknowledged, untouched tenants; successfully stopped owners later acquire a new generation. Unknown computer outcomes remain fenced. If the gateway lost its in-memory journal, abort instead requires read-only proof that every registered tenant and both roles are clean and physically stopped, with no unresolved platform startup. Dirty, uncertain, held or unconfirmed state cannot be converted into a stop receipt. Inspection never starts, checkpoints, stops or repairs a computer. A failed or expired deployment never reopens automatically.

Journal-loss abort preserves the previous gateway's SQL lease. An authenticated request may return 503 until that lease's remaining sixty-second term expires and a new generation starts. Reopening the barrier therefore precedes account readiness; verify the authenticated account and restored workspace/browser data afterward. Do not delete or release an old lease to shorten this wait.

Use the existing deployment identity for recovery. Check out the target release, install locked dependencies, and load the same private environment values with `SIDEKICK_RELEASE` set to that interrupted target SHA. The command returns only operation metadata for `status`; it does not print owner receipts or credentials.

```sh
node deployment/cloudflare/scripts/recover.mjs production status
node deployment/cloudflare/scripts/recover.mjs production abort
node deployment/cloudflare/scripts/recover.mjs production complete
```

Choose `abort` only before activation. Choose `complete` only after activation: it resolves the same release's image tags to digests, checks all selected application rollouts and reruns public smoke before reopening. Completion needs Docker pull access to the Cloudflare registry; expired credentials must be refreshed through Wrangler before retrying. The tool never republishes images, changes the target release, rolls back or clears a fence. A failed image activation needs operator inspection and a compatible forward repair before completion can pass. Do not delete the barrier or substitute a new nonce to bypass a failure. The deployed provider path and interrupted-rollout recovery still need live acceptance; package fixtures alone are insufficient.

Before rollback, inspect the deployed Worker version, all role image references, gateway health release, tenant leases and computer generations/checkpoints. Confirm that the previous code supports the current SQL schema, object/checkpoint format, Durable Object classes and secret version. Stop the exact current generation of the tenant and both computer roles and confirm termination before replacement; never bypass fencing or run a second actor to recover faster. Preserve prior image tags and encryption/derivation keys. Worker rollback does not revert PostgreSQL, R2, optional E2B state or completed external actions, and incompatible Durable Object migrations can prevent rollback. Prefer a forward fix when compatibility is uncertain. A secret rotation also needs a controlled container restart/new image rollout because an already-running gateway retains its startup environment. [Worker rollback limits](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).

The checked-in configuration uses EU placement, private buckets, a 60-second active rollout grace period and disabled automatic request/container logs. Use fixed sanitized health/error reporting rather than recording headers, bodies, connection URLs or startup environment values. Record live Google, provider, webhook, streaming, persistence and cross-user checks separately from the automated substitutes.
