# Server features

`composition.ts` constructs adapters and binds feature factories. `index.ts` serves the app and owns process signals. Other server modules use `../ports` and explicit dependencies; do not import vendor SDKs or concrete runtime/provider implementations. Signal shutdown must attempt application cleanup and database closure independently, return a failing exit status if either fails, and keep raw cleanup errors out of console output.

Read [API contract](../../docs/api-contract.md) before route changes and [security](../../docs/security.md) before boundary changes. The fixed local owner is not public authentication.

`outcomes.ts` owns bounded semantic route preparation and the outcome/pending-input schema. Supply same-owner, exact-channel, current-generation recent conversation, including explicit null outcome provenance, without repeating messages already in candidate transcripts. Read only persisted conversation messages, never secure-entry values. `createUserMessageService` prepares outside transactions; both web and channel ingress apply the prepared decision under the conversation lock. Explicit replies and current waiting-question answers take precedence. Persist related inputs behind an active session, then consume them in order only after a safe idle/question state. Credentials, approvals and manual control keep queued inputs held until their dedicated resume. Cancel/reset discard pending inputs. A router failure uses conversation-only fallback without fabricating an outcome; semantic matching is not a security proof. Keep legacy task rows unclassified.

Create tasks/jobs and source mappings in one transaction. Preserve source IDs, channel identity, and revision checks. Keep one visible conversation while tasks remain internal. A short answer follows the latest visible question in its channel; an explicit message reply must reference an owned message in that channel. A bounded method answer such as Use Google can also continue when that exact option appears in the stored sign-in question. It must not borrow an unrelated question or override channel, explicit-reply or forced-new boundaries. Credential and manual-control waits require their secure path. Action confirmations consume an exact yes/no reply to the stored question in the same owned channel before ordinary conversation routing. Persist waiting states and release workers. Do not replay uncertain external actions.

Channel inbox rows retain the server-generated accepted user message ID. Pass it through composition as `clientMessageId`, including queued inputs. Schedule creation derives its delivery route from trusted task/message provenance or an inherited scheduled-task route, never model recipient arguments. Preserve that route on edits. Dispatch the new task and its `channel_task_routes` entry in one transaction. Outbox delivery uses the original receipt and rechecks account/sender access plus provider reply windows without inventing a new inbound event or retrying uncertain sends.

Web submissions use `clientMessageId` as their persisted message UUID. Under the conversation lock, accept exact retries only when normalized text, ordered attachment IDs, reply target, owner, channel and current generation match. Return the original accepted message/session without repeating routing or dispatch; reject reused IDs with changed content. Queued inputs retain the same ID.

An accepted user execution failure persists one fixed assistant reply in the failure transaction, identified by task and revision. Preserve owner, running-state and current-generation checks; cancellation and stale completions cannot publish. Background failures stay quiet. Private failure diagnostics are best-effort and cannot hold the worker.

Elapsed time never inserts a canned progress reply. The agent can send a concrete useful update through the normal reply path; cancellation and revision checks apply. Web typing/deltas show live work; background work stays quiet unless it has a useful result. Supply the saved IANA preference timezone or the explicit Europe/Lisbon default to runtime; never derive it from the host timezone. `task-progress` covers these boundaries with fake clocks and disposable PostgreSQL.

User reactions to assistant messages create a quiet event only when a non-null value changes and a model is configured. Removing or repeating a reaction does not wake work. Assistant reactions use `createAgentReactionService` and target only owned user messages visible to the active direct-user web segment. Recheck source/target owner, exact channel, current conversation generation and task revision under the conversation lock. Persist one reaction per message and a five-minute cooldown across concurrent segments and restarts; removal does not reset that history. They never create another event. Telegram and WhatsApp reactions are not implemented. Source message IDs are available only for the persisted current user-authored instruction, not synthetic resumes or reactions.

Reset archives the web conversation by advancing its persisted revision and cancelling its active tasks. It never deletes messages, saved context, accounts, Vault entries, goals or schedules, and does not reset other channels. Filter visible chat, routing, runtime history and history search through `currentConversationSql`. New tasks inherit the current channel revision; archived tasks cannot continue or publish. Carry `conversationRevision` through state, stream events and optional message/onboarding requests so late client responses cannot restore archived chat. Validate one emoji grapheme with the shared emoji helper; legacy like, dislike and heart values retain their glyphs and dedupe equivalently.

Validate personal mutations through `personal.validateReview` before deciding whether to execute or confirm, and again in execution preflight. Use the write schemas and owned-target/timing checks, preserving normalized defaults in the reviewed payload. Invalid or obsolete local proposals must not enter uncertain execution. Goal creation supports an explicit next action, status and progress, defaulting to an empty next action, active status and zero progress.

`action-policy.ts` gives exactly five reversible local plan operations a direct path: goal create/update and schedule create/update/cancel. They require the exact current owned user message, current task revision and successful normal preflight; preserve target ownership, timing validation and idempotency. Do not require an English command phrase. The agent must use read tools for requests that only review/list/suggest, respect explicit no-change or draft-only instructions and ask about missing or ambiguous details before proposing a mutation. This is delegated local planning authority, not a semantic or prompt-injection guarantee. Background events, onboarding and synthetic resumes do not gain that authority.

Bind every connected-app write to the selected owned `connectionId`. `action-policy.ts` retains an exact ordinary-operation catalog and conservative phrase/scope matching of the current user instruction for external and other personal writes. This matching can still require confirmation for valid unfamiliar wording; it is not general language understanding. Clear ordinary requests execute without another permission step; unknown, destructive or ambiguous actions persist a specific chat question and exact action/account/arguments snapshot. Draft-only requests cannot transmit. These checks are conservative scope checks, not general semantic or prompt-injection proof. Recheck it at execution; missing or revoked accounts must fail without fallback. Keep watch intent separate from active subscriptions. Verify event owner, account, subscription, and raw signature before dispatch.

`action-presentation.ts` formats readable confirmation questions from allowlisted human fields, without argument dumps or internal identifiers. `approvals.ts` resolves owned goal/schedule titles for updates before formatting. Confirmation questions resolve account labels through `integrations.describeApproval` using the stored connection ID, owner, active provider and action toolkit. Use only the service name and verified cached account name/email; never include provider account IDs, callback values or credentials. This metadata does not grant execution permission.

Onboarding inspects connected apps and proposes useful work without connected-data writes or profile questionnaires. The shared app catalog is `shared/integrations.ts`, and `integration-policy.ts` lists reviewed reads explicitly. Downloads use the owned account and the dedicated file boundary; no model-provided URL or filesystem path is accepted. Supported watches are always requested; missing webhook configuration remains unavailable. Connection links belong in chat and never grant write approval.

Each subscription attempt claims a new `watch_revision`. Reclaimed attempts must fence both successful saves and failure/retry writes to that revision. A stale success removes its unused provider subscription; it cannot overwrite the current trigger.

Derive personal-data provenance from persisted owned user messages, never model arguments. Automatic learning accepts only the supported matching quotes/statements; other changes follow the requested-action policy. External event text cannot choose its own trust level.

Secure forms and channel setup send values directly to trusted services, never chat or model context. Expose status/metadata only. Polling acknowledges an update after inbox persistence; transport changes drain active delivery and recheck the current owner binding. Telegram verification is read-only. Persist the encrypted desired configuration with `registration_pending` before applying its transport or registering the webhook, then mark it registered only after both succeed. Keep that configuration on activation or confirmation-write failure; restoring the old secret could disagree with Telegram. Composition retries pending registration after constructing the channel transport on startup. Failed recovery stays visible and contains no provider payload. Disconnect removes pending ciphertext and prevents recovery.

Return fixed public errors without provider payloads or secrets. Keep schema additions compatible with existing local data. Use disposable schemas for duplicate dispatch, cancellation, restart, stale forms, account migration, and provider replacement tests; see [development](../../docs/development.md).

The owned, inspector-gated screen endpoint returns HTTP 409 with a fixed code/message for recognized `BrowserActionError` failures. Do not expose raw provider messages or relax public-destination checks for browser error pages.

Inspector records are private developer data, not public error logs or telemetry. Mask and bound them before storage. Preserve task ownership, revision fencing, disabled capture, retention and combined timestamp/ID pagination. Unknown prices remain null; do not infer tool fees from model usage. Keep secure broker values outside these events. `inspector.recordFailure` captures accepted failed execution segments in the same private store, including failures before a model opens. Preserve the fixed public error; normalize only Error name/message/code/stack and bounded Error causes, redact before storage, and never copy response bodies or arbitrary error properties. Fence by owner, current conversation and exact failed revision, deduplicate per segment, bound pending capture, and drain it before closing the inspector pool.

`inspector-work.ts` reads current owned executions grouped by outcome, pending input counts, enabled schedules and the last 24 hours of background decisions. Preserve current-conversation filtering for active work, typed review/event sources, redacted bounded labels and total counts before display limits. It reads persisted next occurrences and actual scheduler registration; never fabricate a next heartbeat or expose full task prompts/event summaries. Redacted task titles can be derived from the beginning of a user request. This endpoint does not enqueue work or invoke a provider.

Manual control first bumps the owned task revision, aborts its worker and waits for runtime tools to drain before taking the browser lease. Serialize each task's start, input and resume operations. Recheck owner, waiting reason and exact revision before manual input or resume. Release stale adapter leases when status checks detect cancellation, reset, ownership loss, revision changes or expiry, including before rejecting a new acquisition for a terminal task. Keep cleanup in the same per-task queue as reacquisition; failed release remains retryable. Release browser control before atomically requeueing an inspect-first continuation. Failed acquisition or resume leaves the task paused. Do not persist or log manual input values.

Provider usage stores bounded labels and numeric metrics only. Never capture provider arguments or results there. Stop channel delivery and agent work before closing metering, then drain accepted records before closing its database pool. Keep unknown costs null and distinguish metered operations from provider billing.

Saved profile fields, memories and active goals belong to the owner across approved channels. Task context also includes at most twenty current-generation messages from other owned channels, with provider-only channel labels and no actionable message IDs. Same-channel routing and visible reply/reaction IDs remain separate. History search retains ownership and archive filters and reports channel provenance.

Supply profile and goals through `RuntimeContext.personalContext`, independently of the thirty memory facts. Keep the user's timezone separate. A full memory list must not truncate saved identity, preferences or active goals.

Channel media resolution accepts persisted artifact UUIDs only and rechecks owner plus task. Read the fixed private artifact path without symlinks, bound reads to the stored file size, and cap one delivery at ten files and 15 MiB total. Recheck the channel binding after resolution. A failed read blocks delivery; an uncertain or partially accepted provider send is never automatically replayed. Unsupported transports return local-app attachment guidance.

The Vault broker rejects a form when its fresh inspection finds neither login fields nor methods; never fall back to a stale model-requested kind on such a page. Runtime method choices happen in chat before provider selection or Vault entry. The private form does not provide a second provider chooser. A successful credential injection is not proof the website accepted it. Keep the task/owner/origin-bound staged login through its original ten-minute expiry so identifier-first websites can continue without asking for the same login twice. Saved-identifier injection uses the same bounded association. Rejected website steps consume their old form; a new revision-bound form handles fresh input.

Vault stores separate named entries for the same exact origin. Bare-domain normalization applies only to manual saving, never trusted browser inspection. Secure password submission requires the user's label. Pending form metadata contains matching saved-entry names/hints, never plaintext secrets. `/saved` selects an owned entry under the same token and revision lock. `credential_account_selections` retains an encrypted staged identifier and bounded account selection across continuation. Its identifier label comes from fresh browser inspection, is normalized to at most 80 plain-text characters and survives staged saving/restart. Saved labels are preserved on edit; manual entries infer Email only for a validated email address, otherwise Username. Reject client label overrides; a password-only stage cannot switch identities. Composition calls `fillSelected` before unambiguous automatic reuse. A blocked, expired or missing selection must not silently fall back to another account.

Saved-login viewing uses the UI-only POST routes `/api/vault/:id/details` and `/api/vault/:id/password`. Details return metadata and the full username; only the explicit password route returns a password. Require a UUID and empty body, select the server-owned entry, and preserve its AES-GCM owner/origin/ID binding. Use no-store/no-referrer headers and fixed errors. The private GET Vault list includes full usernames after owner recheck and decryption; broker `vault.list()` and secure account choices remain masked and login-only. Do not expose these private reads through the runtime, provider usage, Inspector or logs.

Saved-login editing uses UI-only `PATCH /api/vault/:id` for the label, username and optional password. Reject origin/owner overrides. Blank or omitted password keeps the latest saved secret. After key access, recheck ownership under a row lock and encrypt with the same exact origin and record ID. Return masked metadata with no-store headers and no plaintext values. Preserve the other accounts on the same website and do not resume or fill a browser from an edit. `vault-update` covers invalid/foreign inputs, key and ownership races, blank-password preservation and restart. Vault shutdown stops its retry timer, drains the currently accepted credential resume, and leaves later pending rows for the next server instance. No resume sweep starts after close.

Payment cards use the separate `vault_cards` table and `sidekick-vault-card-v1` owner/record binding. Keep all login matching on `vault_entries`; cards must never enter `vault.list()`, saved choices, invitations or browser injection. Card lists contain only name, brand, last4 and expiry. Details add the cardholder and code presence only; explicit POST `/api/vault/:id/card-number` and `/security-code` return only the requested secret. Security codes are optional three/four-digit strings inside the encrypted card payload, absent from lists and runtime. Reject unknown fields, invalid codes, Luhn and expiry. Normalize spaces/hyphens before encryption. Card updates lock and recheck owner after key access, preserving the latest number when omitted and the latest code when omitted or blank. A supplied blank card number is invalid. Explicit `securityCode: null` removes it. Legacy cards without a code remain readable. All card routes use no-store/no-referrer and fixed errors. Do not expose card management or purchase tools to the agent.

When the browser reports a fresh rejection, consume the old token and issue a new form in the same transaction, with the same expiry and task revision. Do not save the rejected password or resume the model. Return HTTP 200 with `{ok:false,retryUrl,error}` so the form can replace its token and clear inputs. Unknown submission results still require inspection and must not be called authenticated.

Direct UI deletion uses owned `DELETE /api/goals/:id` and `DELETE /api/schedules/:id` routes with UUID validation. Delete only the chosen local record; missing or foreign IDs return 404 without a mutation. Goal deletion preserves chat history and other goals. Schedule deletion locks the row and cancels its queued job in the same transaction, preserves independent run snapshots and fences already-claimed jobs. A cancellation failure must retain both schedule and pending work. These destructive delete routes are not part of the agent’s reversible plan catalog.

Schedules persist an exact next occurrence and queued job ID. Both once and recurring work use delayed pg-boss jobs; cron preview computes recurring dates in the saved timezone. Update/pause/delete must cancel the pending job and increment or remove its schedule revision in the same transaction. Dispatch locks the schedule and checks job ID, revision and occurrence before creating the internal task, run snapshot and next job atomically. A delayed recurring occurrence runs once, then advances to the next future occurrence; do not replay every missed interval. One-off schedules disable after dispatch. History snapshots survive schedule deletion and report actual execution status, not proof of an achieved user outcome. Startup removes legacy cron registrations and reuses/reconciles pending delayed jobs. Do not reset the normal owner data to test migration.

`inspector-prompts.ts` stores optional effective agent prompt snapshots privately. Check owner and current execution revision, redact before persistence and on displayed titles, bound pending writes and string sizes, and retain seven days. Disable access/new capture with the inspector flag, but prune expired owner snapshots at startup and hourly even while disabled. Stop and drain retention work on close. Apply bounded structured masking to JSON embedded in prompt/failure prose, including nested serialized JSON; omit incomplete or oversized structured data. Reapply prompt masking when reading older stored snapshots. Never send these snapshots to ordinary logs, usage telemetry or agent tools. Close and drain it before the inspection pool.

`approvals.acceptChat` runs under the existing conversation transaction after idempotency checks. It binds consent to the displayed assistant message, same channel/generation, pending task revision and expiry; attachments and changed-action prose are not consent. It stores the user decision and queues a new revision atomically without calling a provider. `executeConfirmed` claims that exact revision once in the worker, rechecks account/target preflight and preserves uncertain outcomes after an interrupted external action. Declines resume without execution. Cancellation or reset before the claim blocks it. No action-review HTTP page is required.

`action-policy.ts` recognizes the exact Goals review draft only when an explicit change follows it. Goal completion and resume phrases apply only to goal updates. Schedule change and resume phrases apply only to schedule updates. Do not extend these rules to app sends or remove draft, negation, scope or source-message checks.

A segment uses `tasks.source_message_id` for the user instruction it is executing. Pending later inputs stay out of model history and uploads until consumed. Personal action provenance must match that source, its task/owner/role and current prompt; synthetic resumes have no new direct-user evidence. Credential completion and manual-control release record a trusted resume kind and exact task revision. Only known ordinary app operations may consult the still-owned original source on that revision; background, onboarding, unknown actions and personal writes cannot use this exception. Vault passes its saved request revision to resumeTask, so a delayed old completion cannot release a newer wait. Deduplicate completed writes by task, original source, exact action and arguments across these resumes; confirmed-action resumes clear source evidence and cannot replay their snapshot. Never replace this with the latest message in the session.

Core browser metadata, ordinary frames and takeover use `/api/browser` independently of the Inspector flag. Take control uses `/api/browser/control/:taskId/start`; the sign-in route remains a compatibility alias. Accept no client URL. The workspace path maps to an owner-bound server identity and creates no task. Terminal control binds a new process-random revision to the exact terminal task status/revision; Done restores masked viewing without task resume. Active work retains pause/drain/resume. Keep its owned revision, drain-before-open and close-only stale cleanup. Only the active owned `sign_in` lease may read `/sign-in-screen?revision=N` or send native desktop input; recheck ownership, revision and expiry after capture and discard late bytes. Frames are no-store and never enter Inspector, artifacts, provider usage or logs. Ordinary/model screenshots remain blocked. Explicit resume finishes native sign-in before releasing control and requeueing; failed restoration leaves work paused. Meter bounded open/finish operations without private inputs or URLs. Inspector-prefixed aliases remain flag-gated.

Workspace publication requires the optional `Workspace.readArtifact` capability and fails closed when it is absent. The container reads a bounded regular file through no-follow descriptors; the server never validates a host path and then reads it later. Roll back the newly written private artifact if its database insert fails. Personal memory proposals use the same bounded credential filter as automatic learning; declined profile answers are not personal facts.

Apps lists persisted account identity and last verified active state immediately. Coalesce background health checks, run at most four together and retain the previous state on provider errors. Successful inactive results update the saved state. Watches retry failed setup with persisted backoff, including old incomplete attempts without a timestamp. Destructive app proposals must name a recent exact account-bound read target; absent targets require a fresh read before confirmation.

Scheduled runs copy their owned user instruction and operational prompt into immutable run metadata. Only known ordinary app operations matching both can execute; draft/no-send, cross-app and generic event sources cannot borrow this authority. Prompt edits replace the grant, while timing-only edits retain it. Do not infer scheduled authority from the model-generated task prompt or source flag alone.
