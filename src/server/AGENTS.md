# Server features

`browser-connections.request` is the model-facing preflight. Reject invalid arguments, absent owner-bound session IDs, unsupported session states and mismatched stored origins before binding or navigating. `use` accepts saved or needs-sign-in sessions; `connect` also accepts pending sessions for renewal. Reject disconnecting and unknown states for both. Preserve cancellation after the read; do not recover database failures, state races or errors from delegated `begin`/`use`. HTTP routes retain their ordinary validation and error responses. `integrations.manageConnections` adds model-only `browserAccess` metadata for saved credentials versus saved or reconnectable browser sessions. Pending and disconnecting sessions must not advertise reusable access; keep Apps connection IDs and Vault removal semantics unchanged.

`runtime-host.ts` derives `OTTO_COMPOSIO_WEBHOOK_URL` for each tenant from the canonical HTTPS `OTTO_WEBHOOK_ORIGIN` or public application origin. HTTP loopback development without a tunnel leaves it absent. Reject malformed explicit origins before starting a tenant; never copy a caller-supplied internal URL. Composition passes this fixed destination to the adapter for new watches. Existing account/trigger ownership and raw-body signature checks still apply, and saved trigger IDs are not automatically migrated.

`runtime-host.ts` serves user and webhook requests for a ready tenant without `deploymentClosed()`, because the Cloudflare gateway Durable Object already reads the same barrier for each public API request. Keep that check for `kind:'wake'` and before every tenant start, including `warm`. The in-process deployment state still rejects ready tenants during a drain. `gateway.ts` calls `warm` without waiting after a signed-in `/api/session` read; it shares the per-owner pending start and never blocks or fails the session response. Only `/api/events` rechecks the session after the tenant answers.

`browser-connections.ts` owns saved website sessions. Keep its token hash, owner check, active-thread check and running-turn claim on each sign-in or reuse step. Serialize reuse, reconnect and removal for one connection. Carry turn cancellation into browser work. Lock and recheck the active thread before credential injection; an archived thread must not submit. Update the last page check time after successful reuse; that time does not prove account access. The server supplies a private profile ID; the client and model cannot select one. Inspect live login fields before credential entry. Accept a different login origin only on another HTTPS subdomain of the same registered site and port. Keep passwords and codes out of chat, model input and stored connection rows. A submitted login step is not proof that the website accepted it. Check the current page for verification fields before opening the requested address. Keep a requested Vault login in process memory until the session check passes; discard it on expiry or a new sign-in. A blocked site must give a clear error. Keep a failed disconnect in the disconnecting state for a safe retry; never report deletion before the browser profile is removed.

`composition.ts` constructs adapters and binds feature factories. `index.ts` serves the app and owns process signals. Other server modules use `../ports` and explicit dependencies; do not import vendor SDKs or concrete runtime/provider implementations. Signal shutdown must attempt application cleanup and database closure independently, return a failing exit status if either fails, and keep raw cleanup errors out of console output. Retain the tenant lease until cleanup finishes so its existing expiry watchdog can terminate pending cleanup. Repeated signals must not extend that deadline.

`thread.ts` returns text from an owned CSV download to the agent only when the file has valid UTF-8 and is at most 12,000 bytes. Keep the saved chat artifact separate from that text. Do not return provider download URLs or base64. Keep running-turn and cancellation checks around file delivery.

`integrations.ts` keeps the Apps catalog and saved account provider ID. New Notion and Linear attempts use the direct MCP adapter; saved Composio Notion accounts still route to Composio. Direct tool discovery receives only active saved account IDs. Chat consent attempts bind owner and turn; a completed callback queues one `resume` turn for that turn. The Apps route returns to the configured app origin. Keep direct tokens inside the trusted Vault and adapter boundary, and preserve account-specific revocation and read policy. `direct_oauth_accounts` holds metadata; startup moves older ciphertext to `vault_app_grants`.

`discovered-connections.ts` owns model-proposed public HTTPS MCP, HTTP API, and installed CLI paths. `vault-app-grants.ts` owns their encrypted grants and pending OAuth state. Connection rows hold path and account metadata only. Startup moves legacy saved grants into Vault and clears their old ciphertext. An HTTP path needs a valid GET test address before the secure form opens. A path change needs a new sign-in or token check. Route all non-read calls through the current approval service. Provider adapters keep OAuth discovery, PKCE, DNS checks, address pinning, HTTPS and redirect limits outside the feature. Do not pass tokens into Pi, the shell, browser or approval arguments. Apps also lists saved website logins as browser paths from Vault. Removing one from Apps removes the same Vault login. Browser session cookies stay in the private browser profile. A saved CLI path sends one Vault token to the selected program through a separate computer user. The ordinary shell has no Vault read path. A selected CLI can send or save its token, so use only a trusted program. Cloudflare computer mode cannot accept CLI proposals.

Deployment drain is separate from process shutdown. `work-admission.ts` admits pending starts synchronously; `tenant-drain.ts` pauses normal HTTP ingress and registered pg-boss consumers without aborting accepted turns. Stop each consumer by its exact worker ID with `wait:true`; a late stop must never target a replacement worker. Track detached integration refreshes, watch/event processing, Vault retries and channel batches through admission. Already accepted queue callbacks finish naturally, including callbacks blocked before their model controller exists. Queued work remains durable for resume or the next process. A tenant receipt requires stopped consumers and zero admitted work before its absolute deadline. HTTP response or client disconnect alone cannot release a handler still running. Lease renewal and signed deployment control remain available; existing read-only SSE streams do not prevent drain. Timeout or stop failure leaves admission paused. Only the same nonce, release and deadline may resume; exact successful resume is retryable, and cannot reopen a newer drain. `stopThreadWorkers` still aborts the running turn on shutdown, including a start that races its controller registration. For E2B, the optional computer lifecycle pauses the shared owner sandbox only after natural work drain, and adds `computerPaused:true` only after acknowledged pause. Abort waits for any pending pause before resuming that same computer and then its consumers; uncertainty keeps ingress paused. Ordinary shutdown sends the fixed generation-bound private computer stop acknowledgement only after both runtime capabilities dispose successfully. A tenant drain receipt does not prove confirmed hosting-container stop; Cloudflare computer checkpoint/stop proof remains separate.

`thread.ts` owns the single-thread model described in [single thread](../../docs/single-thread.md). Each owner has one active `threads` row, shared by web, Telegram and WhatsApp; its ID keys the Pi session, workspace sandbox and browser computer. User messages, schedule fires, triage wakes, reactions and resumes each insert a `turns` row and send a `thread-drain` job in the same transaction. The drain worker takes the schema-scoped per-owner thread lock, claims the oldest queued turn only while the thread is `idle`, and runs one turn at a time. Drain bookkeeping retries durably after a database error and settles an interrupted running turn before claiming another; it never replays the interrupted turn. Starting a later turn cancels older credential and browser waits, and secure resumes require the matching current wait and active thread. Every write from a turn goes through `withTurnLock`, which requires that turn to be `running` on the active thread; stopped, cancelled and archived turns get the fixed 409. A question, approval or credential request ends the turn `waiting` with a display-only `waiting_reason`; the next user message is simply the next turn. `POST /api/thread/stop` aborts the running turn and cancels queued turns. Nothing is retried automatically: an error, the 20-minute turn limit or a restart ends the turn `failed` with one fixed message asking the user to check anything started outside or say continue; background turns stay quiet. Public message, history and onboarding requests may carry the client's `threadId`; a stale one returns 409.

Create turns, drain jobs and source mappings in one transaction. Preserve source IDs (unique per owner) and each turn's reply channel. Keep one visible conversation; turns remain internal. An explicit message reply must reference an owned message in the active thread. Action confirmations consume an exact yes/no reply to the stored question on the same channel before a new turn is created. Credential and manual-control waits require their secure path. Persist waiting states and release the worker. Do not replay uncertain external actions.

Channel inbox rows retain the server-generated accepted user message ID. Pass it through composition as `clientMessageId`. Intercept exact verification codes before inbox persistence. A recognized verification conflict atomically stores a masked discarded receipt, a fixed guidance message with no turn and its explicit outbox route; never route the code to a model or create a turn for the notice. Other hook or database failures return a fixed 503 without acknowledging the receipt. Schedule creation derives its delivery route from the creating turn's channel and its latest owned inbox receipt, never model recipient arguments. Preserve that route on edits. Outbox delivery sends a turn's assistant messages through the latest owned receipt for that turn's channel and rechecks message owner, account/sender access and provider reply windows without inventing a new inbound event or retrying uncertain sends.

Web submissions use `clientMessageId` as their persisted message UUID. Under the thread lock, accept exact retries only when text, ordered attachment IDs, reply target, owner and active thread match. Return the original accepted message and turn without another dispatch; reject reused IDs with changed content.

A failed foreground turn persists one fixed assistant reply in the failure transaction, identified by turn. Preserve owner, running-state and active-thread checks; cancellation and stale completions cannot publish. Background failures stay quiet. Private failure diagnostics are best-effort and cannot hold the worker.

Elapsed time never inserts a canned progress reply. The agent can send a concrete useful update through the normal reply path; cancellation and running-turn checks apply. Web typing/deltas show only foreground turns in the exact `web` channel. Internal delta events carry immutable owner/channel identity; `/api/events` independently verifies both and removes routing metadata before writing bytes. Web state turn metadata also excludes external channels. Preserve background web replies through persisted state and refresh events; `channel-stream-isolation` exercises the actual turn-to-SSE path. Background work stays quiet unless it has a useful result. Supply the saved IANA preference timezone or the explicit Europe/Lisbon default to runtime; never derive it from the host timezone. `thread-progress` covers these boundaries with fake clocks and disposable PostgreSQL.

User reactions to assistant messages create a quiet event only when a non-null value changes and a model is configured. Removing or repeating a reaction does not wake work. Assistant reactions use `createAgentReactionService` and target only owned user messages in the active thread during a running direct-user web turn. Recheck source/target owner, exact channel, active thread and running turn under the thread lock. Persist one reaction per message and a five-minute cooldown across turns and restarts; removal does not reset that history. They never create another event. Telegram and WhatsApp reactions are not implemented. Source message IDs are available only for the persisted current user-authored instruction, not synthetic resumes or reactions.

Reset archives the active thread for every channel, cancels its queued and running turns, and creates a new thread in the reset transaction; the next turn starts a new Pi session, workspace and computer. It never deletes messages, saved context, accounts, Vault entries, goals or schedules. Filter visible chat, runtime history and history search through `activeThreadSql`. Archived turns cannot publish. The client sends the `threadId` from state with messages and onboarding requests so late client responses cannot write to an archived thread. Validate one emoji grapheme with the shared emoji helper; legacy like, dislike and heart values retain their glyphs and dedupe equivalently.

Validate personal mutations through `personal.validateReview` before deciding whether to execute or confirm, and again in execution preflight. Use the write schemas and owned-target/timing checks, preserving normalized defaults in the reviewed payload. Invalid or obsolete local proposals must not enter uncertain execution. Goal creation supports an explicit next action, status and progress, defaulting to an empty next action, active status and zero progress.

`action-policy.ts` gives exactly five reversible local plan operations a direct path: goal create/update and schedule create/update/cancel. They require the exact current owned user message, the running turn and successful normal preflight; preserve target ownership, timing validation and idempotency. Do not require an English command phrase. The agent must use read tools for requests that only review/list/suggest, respect explicit no-change or draft-only instructions and ask about missing or ambiguous details before proposing a mutation. This is delegated local planning authority, not a semantic or prompt-injection guarantee. Background events, onboarding and synthetic resumes do not gain that authority.

`startOnboarding` does not start a welcome while a user turn is queued or running on the active thread. Keep this check under the thread lock. Account consent must resume through its own `resume` turn without an overlapping welcome offer.

Bind every connected-app write to the selected owned `connectionId`. `action-policy.ts` retains an exact ordinary-operation catalog and conservative phrase/scope matching of the current user instruction for external and other personal writes. This matching can still require confirmation for valid unfamiliar wording; it is not general language understanding. Clear ordinary requests execute without another permission step; unknown, destructive or ambiguous actions persist a specific chat question and exact action/account/arguments snapshot. Draft-only requests cannot transmit. These checks are conservative scope checks, not general semantic or prompt-injection proof. Recheck it at execution; missing or revoked accounts must fail without fallback. Keep watch intent separate from active subscriptions. Verify event owner, account, subscription, and raw signature before dispatch.

After one confirmed discovered-app write, retain the original owned user message only for the `resume` turn that executes it. A later write must still pass account preflight and receive its own confirmation. Do not treat the confirmation reply or provider result as a new instruction. An unrelated turn or later user message must not inherit this provenance.

Derive personal-data provenance from persisted owned user messages, never model arguments. Automatic learning accepts only the supported matching quotes/statements; other changes follow the requested-action policy. External event text cannot choose its own trust level.

A user turn's `message_id` is the instruction it executes. Personal action provenance must match that source, its turn/owner/role and current prompt; synthetic resumes have no new direct-user evidence.
